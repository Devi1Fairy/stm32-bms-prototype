# 首次上板：PB5与D3闪烁

日期：2026-10-17。本步唯一目标：由自己的固件控制板载D3亮约0.5 s、灭约0.5 s，并确认复位及单独USB供电后仍能运行。GPIO配置与循环已由用户实现，最新Keil构建0错误0警告。曾出现ST-LINK失电但RST仍连接时D1亮、D3灭；用户现已确认单独移除RST即可恢复闪烁，定位到外部复位连线条件。具体NRST电平未测量；完整冷启动、复位及10周期验收仍按下文收尾。

## 引脚与接线依据

使用本地《[野火]STM32F103ZET6核心板双USB款原理图》，共7页。LED区域在第6页，该页标题栏为V2.0、2023-11-04；不同页的版本标注不完全一致，实物PCB版本仍待补充。

第6页LED区域已渲染并目视核对：

| 板上器件 | MCU引脚 | 串联电阻 | 有效电平 |
| --- | --- | --- | --- |
| D3，BLUE | PB5 | R20，470 Ω | 低电平亮、高电平灭 |
| D4，BLUE | PB0 | R21，330 Ω | 低电平亮、高电平灭 |
| D5，BLUE | PB1 | R22，100 Ω | 低电平亮、高电平灭 |

本步只控制D3。它已焊在板上，无需新增LED、电阻、面包板或信号线；沿用开发板USB供电和已有SWD连接。

D3电流路径为3V3→LED→R20→PB5。PB5输出低电平时吸收电流，LED导通；输出高电平时两端压差不足，LED熄灭。由实际电路决定亮灭，不能假定所有LED都是高电平亮。

配套标准外设库例程的引脚与低有效定义可交叉参考，但其红绿蓝、SCL等旧注释不匹配当前三颗蓝灯。当前工程使用HAL，不复制旧例程的标准库初始化。

## 第一步：CubeMX配置PB5

打开现有MCU/projects/bms_bringup/bms_bringup.ioc，不另建项目。当前HSI 8 MHz及SYS Serial Wire配置保持。

在Pinout中选择PB5为GPIO_Output，再进入System Core → GPIO，设置PB5：

| 配置 | 选择 | 原因 |
| --- | --- | --- |
| GPIO output level | High | D3低有效，初始化时先保持熄灭 |
| GPIO mode | Output Push Pull | 引脚可主动输出高和低电平 |
| GPIO Pull-up/Pull-down | No pull-up and no pull-down | 推挽输出不依赖内部上拉下拉 |
| Maximum output speed | Low | 足够驱动慢速LED；不是闪烁频率 |
| User Label | LED_STATUS | 生成可读的端口和引脚名称 |

F1的Low档对应2 MHz输出速度等级，用来控制输出驱动特性，不会让D3自动以2 MHz闪烁。闪烁节奏由下面的程序延时决定。

在Project Manager → Code Generator确认Keep User Code when re-generating已勾选。目前.ioc中的KeepUserCode已经为true，界面再确认后生成。用户代码写在USER CODE标记范围内，CubeMX才按这些区域保留；参见[ST CubeMX手册](https://www.st.com.cn/resource/zh/user_manual/um1718-stm32cubemx-for-stm32-configuration-and-initialization-c-code-generation-stmicroelectronics.pdf)。

使用现有CubeF1 1.8.7生成代码，不在这一步同时升级库或修改时钟。

## 第二步：检查自动生成结果

main.h应出现类似定义，由CubeMX生成，不重复手写：

```c
#define LED_STATUS_Pin GPIO_PIN_5
#define LED_STATUS_GPIO_Port GPIOB
```

LED_STATUS_GPIO_Port表示GPIOB端口，LED_STATUS_Pin表示PB5引脚掩码。GPIO_PIN_5不是直接传数字5，而是第5位对应的位掩码，使用生成的名称即可。

用户本次启用了外设分文件生成：MX_GPIO_Init()实际位于Core/Src/gpio.c，声明在Core/Inc/gpio.h，main.c包含gpio.h并调用该函数。初始化在独立文件是正常生成形式，不需要移回main.c。新增gpio.c/h与已变化的.mxproject应随本次工程保存。

MX_GPIO_Init()应包含这些关键配置：

- 开启GPIOB外设时钟，保证GPIOB可以配置和使用。
- 将PB5的输出值预设为GPIO_PIN_SET，即高电平、D3灭。
- 将PB5配置为GPIO_MODE_OUTPUT_PP、GPIO_NOPULL、GPIO_SPEED_FREQ_LOW。
- 用HAL_GPIO_Init初始化GPIOB。

检查bms_types.h的用户区include和已有BMS C/H仍保留。回到Keil时允许重新载入工程；Application/User/Core应仍有先前添加的保护、状态机、恢复和控制器模块。若工程重新生成后没有保留用户添加的文件条目，按原方法把相应C/H重新加入，电脑测试文件不加入MCU工程。

## 第三步：编写带注释的循环

在VS Code打开Core/Src/main.c。保留HAL_Init()、SystemClock_Config()和MX_GPIO_Init()，将USER CODE BEGIN WHILE到USER CODE END 3这一段调整为：

```c
/* USER CODE BEGIN WHILE */
while (1)
{
  /* USER CODE END WHILE */

  /* USER CODE BEGIN 3 */

  /* D3低电平亮：把PB5拉低，让电流流过LED。 */
  HAL_GPIO_WritePin(LED_STATUS_GPIO_Port, LED_STATUS_Pin, GPIO_PIN_RESET);

  /* 保持亮灯约500毫秒；当前主循环在这里等待，SysTick中断继续计时。 */
  HAL_Delay(500u);

  /* D3高电平灭：把PB5拉高，LED两端不再有足够的导通电压。 */
  HAL_GPIO_WritePin(LED_STATUS_GPIO_Port, LED_STATUS_Pin, GPIO_PIN_SET);

  /* 保持灭灯约500毫秒，再进入下一轮。 */
  HAL_Delay(500u);
}
/* USER CODE END 3 */
```

这里GPIO_PIN_RESET表示输出低电平，不是复位CPU；GPIO_PIN_SET表示输出高电平。

HAL_GPIO_WritePin负责设定引脚状态，HAL_Delay等待以毫秒为单位的时基。现有SysTick_Handler会调用HAL_IncTick()，默认每1 ms更新HAL时基，HAL_Delay据此等待。

HAL_Delay是主循环忙等待，不是让CPU休眠或让出FreeRTOS任务；在等待期间，正常使能的中断仍可执行。本步用于验证GPIO和HAL时基，后续周期采样、控制任务会使用合适的非阻塞调度或RTOS延时。

两次500 ms合起来形成约1 s亮灭周期，不把HAL延时当作精密时间测量。D3当前仅是GPIO演示输出，尚未映射BMS状态，也不代表物理负载开关。

## 实际问题记录：断开ST-LINK USB后不闪烁

### 已有现象与检查

用户补充“d1亮，拔了USB，d3直接不亮”。尚未明确三根SWD线已拔掉或已完全断电，暂不把它等同于“完全脱离调试器冷启动失败”。

只读检查未发现PB5标签、GPIOB时钟、推挽输出或SysTick_Handler缺失。main.c已调用MX_GPIO_Init，LED循环已写入；新构建MAP引用GPIO写入和HAL延时，编译0错误0警告。这里只核对软件结构，不能替代实物供电、实际Flash或启动路径验证。

本地HEX头部初始栈顶为0x20000670，复位向量0x080001CD，与MAP对应；它是电脑产物检查，不是对目标Flash的读回。本次main代码段入口为0x08000BC4，旧寄存器截图对应的0x0800093C不再作为新固件地址使用。

### 下一小步：完全脱离调试器后冷启动

1. 如果仍处于Keil调试模式，先通过Ctrl+F5退出。
2. 拔掉开发板USB和ST-LINK USB，确认D1完全熄灭。
3. 在断电状态移除SWDIO、SWCLK、GND以及任何其他调试器连线，板卡与ST-LINK完全分开。
4. BOOT跳帽保持现状，先不修改代码。
5. 只给开发板左侧USB TO UART接USB供电，打开板卡电源，观察D1及D3至少5 s。
6. 记录D3是否恢复闪烁；若恢复，再按板载RESET观察一次。

这个复测把供电重启与调试器信号连接条件固定下来。若恢复运行，只能先说明原测试条件与独立冷启动结果不同，尚不能唯一确定是调试状态还是外部连线影响；若仍失败，再核对BOOT配置和实际启动路径。

以上是先前的待复测方案；用户后续的RST单线复测已经缩小问题范围，结果及解释见下一节。没有改写矢量表、恢复出厂固件或并接调试器电源。D1亮仍不等于3.3V实测或CPU运行证据。

### 后续复测：确认RST连接影响

用户先确认全部拆线即可恢复，再补充失败时除SWDIO/SWCLK/GND外还接了RST，未接供电线，最后确认仅拔掉RST即可恢复闪烁。这是本次实际找到的接线条件，不再把问题笼统归为“LED代码尚未运行”。

NRST是低有效复位输入：

| NRST状态 | CPU行为 |
| --- | --- |
| 保持低电平 | 处于复位状态，不能正常执行LED循环 |
| 恢复有效高电平 | 解除外部复位，按启动配置进入程序 |

原理图第6页的R19为10 kΩ，上拉NRST到3V3；SW3复位键按下时将NRST接地。ST-LINK的RST线也接在这个节点上，它可以影响节点电平，并非单纯传送一条软件命令。

最可能的解释是失电调试器的RST输出端或内部保护/外围路径影响NRST，使其保持低电平或不能稳定释放；这相当于外部电路持续影响复位。移除RST后，板上上拉恢复节点高电平，LED循环能够执行。D1由供电驱动，所以CPU保持复位时仍可能亮。

已验证的是RST连线条件与闪烁恢复的关系；没有测量NRST电压或拆解调试器，不能把具体钳位、漏电或回灌路径写成已确定的根因，也不据此认定调试器损坏。若以后需要确认电气机理，可对比两种条件下的NRST电压；本次并未进行该测量。

资料依据：本地RM0008英文Rev15第7.1.1节，PDF第90页；对应[ST官方RM0008](https://www.st.com/resource/en/reference_manual/cd00171190-stm32f101-103-105-107-stm32f100-series-armbased-32bit-mcus-stmicroelectronics.pdf)。[ST AN4899第6.3节](https://www.st.com/resource/en/application_note/dm00315319-stm32-gpio-configuration-for-hardware-settings-and-lowpower-consumption-stmicroelectronics.pdf)说明未供电接口的电流路径需要结合引脚电路分析，只支持一般机理，不证明本兼容调试器内部的具体路径。

- 当前三线SWD调试使用Normal，RST留空；独立运行时完全移除调试器连线。
