## 软件环境与首次编译

本章按首次搭建时的工程讲解；其中 HSI、空主循环或未配置外设是当时的状态。当前已使用 HSE/PLL、周期 ADC 和 UART，见[开发记录](开发记录.md#current-status)。

### 已确定的工具组合

**传统 STM32CubeMX 6.x＋Keil MDK＋STM32CubeF1 MCU Package＋STM32F1 器件支持包＋Git**。

~~~text
CubeMX：选芯片、配置外设、生成 HAL 工程
     ↓ MDK-ARM 工程
~~~

### 两种“F1 包”不要混淆

- **STM32CubeF1**：ST 的 MCU 软件包，提供 HAL 等源码，在 CubeMX 中管理。[ST 产品资料](https://www.st.com/en/embedded-software/stm32cubef1.html)
- **STM32F1xx_DFP**：Keil 的器件支持包，让 Keil 识别芯片及使用相关调试/下载支持，在 Keil Pack Installer 中管理。[Keil 包说明](https://www.keil.arm.com/packs/stm32f1xx_dfp-keil/boards/)

本机已有 DFP 文件，不代表 CubeF1 也已安装。CubeMX 生成的 HAL 工程会带入所需驱动文件，不能再凭名称重复添加标准外设库或另一套启动文件。

FreeRTOS 是编入 MCU 固件的内核源码，先完成裸机验证，后续再启用/整合并记录版本。

### 练习 02：阅读当前 main.c

目标：读懂现有初始化顺序，用源码说明当前时钟和 GPIO 做了什么。本轮不修改固件；用户理解验收尚未完成。

打开 MCU/projects/bms_bringup/Core/Src/main.c，忽略空白和 USER CODE 注释后，main() 的当前结构为：

```c
int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();

    while (1)
    {
    }
}
```

| 位置 | 当前工程中的作用 | 阅读依据 |
| --- | --- | --- |
| HAL_Init | 初始化 HAL 基础支持，配置中断优先级分组和默认 1 ms SysTick 时基，调用 HAL_MspInit | main.c 第 74 行；Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal.c |
| SystemClock_Config | 选择内部 HSI 8 MHz，不使用 PLL，AHB/APB1/APB2 均不分频 | main.c 第 108 行起；SYSCLKSource=RCC_SYSCLKSOURCE_HSI |
| MX_GPIO_Init | 当前只开启 GPIOA 外设时钟，尚无 LED 或负载引脚的初始化 | main.c 第 145 行起；__HAL_RCC_GPIOA_CLK_ENABLE() |
| while(1) | 初始化完成后持续执行的主循环；目前循环体为空 | main.c 第 95 行起 |

在 Keil 中把光标放在函数名上，用右键 Go To Definition（或界面提供的同类操作）阅读函数。全工程搜索定位 RCC_SYSCLKSOURCE_HSI 和 __HAL_RCC_GPIOA_CLK_ENABLE，核对结论来自源码。

复位后的整体顺序为：启动文件 Reset_Handler → SystemInit → C 运行库 __main → main。SystemInit 在 main 之前建立底层系统环境；C 运行库完成数据段初始化等工作；main 中的 SystemClock_Config 再设置应用选定的时钟。先区分这些职责，启动文件细节后续再展开。

本次 MAP 的大小解释：Flash/ROM 为 2096+372+16=2484 B；链接分配的 RAM 为 16+1632=1648 B，包含当前预留的 1024 B 栈和 512 B 堆。它是链接结果，不是运行时峰值测量。[Keil 对构建大小的说明](https://www2.keil.com/docs/default-source/default-document-library/gs_ds-mdk_5_27_r0.pdf?sfvrsn=4)

本步验收：能按顺序说明四段代码的作用，从 SystemClock_Config 指出当前系统时钟来源与频率，并说明目前 GPIO 初始化是否配置了输出引脚。阅读并理解通过后，再进入下一项独立 C 逻辑练习。

## 最小工程的逐项配置解释

本章按首次搭建时的工程讲解；其中 HSI、空主循环或未配置外设是当时的状态。当前已使用 HSE/PLL、周期 ADC 和 UART，见[开发记录](开发记录.md#current-status)。

### 安装 STM32CubeF1 1.8.7

CubeMX 根据图形配置生成初始化代码，STM32CubeF1 提供这些代码依赖的 F1 系列 HAL、CMSIS 和示例等源码。HAL 是 ST 提供的硬件抽象层，例如 HAL_GPIO_Init 将引脚配置转换为寄存器操作；CMSIS 提供 Cortex-M 内核与器件相关的基础定义。

安装库是让电脑上的 CubeMX 能取得代码，并没有把固件写入 MCU。用户已确认 1.8.7 安装成功，本机也检查到对应包目录和必要文件。

若通过 Help → Manage embedded software packages → From Local 安装，应选择完整软件包 ZIP，工具负责检查和解包；具体实际安装途径尚未由用户补记。1.8.7 的 package.xml 声明基础版本为 1.8.0、补丁为 1.8.7，当前安装目录已有必要基础文件，不需重新下载或降级。

CubeMX 6.18.0、CubeF1 1.8.7、Keil 5.24 和 Compiler 5.06 是不同组件的版本号，无需彼此相同。[ST CubeF1 说明](https://www.st.com/en/embedded-software/stm32cubef1.html)

### 在 MCU Selector 中选择 STM32F103ZETx

操作：搜索 STM32F103ZE，选择对应器件，核对 LQFP144、512 KiB Flash 和 64 KiB RAM，再点击 Start Project。

芯片型号决定可配置的引脚、外设、寄存器与存储器容量。当前 .ioc 的具体订货型号为 STM32F103ZET6，通用器件显示名为 STM32F103ZETx；x 表示此处按通用型号归类。其他容量的 F103 不能仅因属于同一系列就替代。

Flash 用于存放掉电后仍保留的程序和常量等；RAM 用于程序运行中的变量、栈、堆等。LQFP144 表示相应封装具有 144 个引脚，选它是为了匹配已订购的 MCU。

使用 MCU Selector，是按芯片创建工程。第三方核心板的实际板载 LED、晶振和接口仍要看板卡原理图，芯片型号本身不能告诉 CubeMX 这些板级连接。[ST 器件资料](https://www.st.com/en/microcontrollers-microprocessors/stm32f103ze.html)

验证：.ioc 的 Mcu.CPN=STM32F103ZET6、Mcu.Package=LQFP144；Keil 目标为 STM32F103ZE，Flash/RAM 地址范围匹配。

### SYS → Debug → Serial Wire

选择 Serial Wire，使芯片保留 SWD 下载调试接口。ST-LINK 后续通过该接口访问 MCU，支持下载程序、暂停执行、断点和查看变量。

SWD 的两个主要信号是 PA13/SWDIO（调试数据）和 PA14/SWCLK（调试时钟）。真实接线还需确认地参考和供电/电压参考；本步骤只是保留接口，尚未接线。

选择它的原因是当前使用独立 ST-LINK，SWD 能满足下载调试需求，且只占用两个主要调试信号引脚。当前 HAL_MspInit 中生成 __HAL_AFIO_REMAP_SWJ_NOJTAG()，关闭 JTAG 并保留 SWD。

验证：.ioc 中 PA13、PA14 的 Mode 为 Serial_Wire；源文件 Core/Src/stm32f1xx_hal_msp.c 有上述 SWD 保留设置。

### 保持内部 HSI 时钟

CPU 和外设计时依赖时钟。HSI 是芯片内部的 RC 振荡器，F103 的标称频率为 8 MHz；HSE 通常来自板上的外部晶体或时钟输入；PLL 是可用于倍频的锁相环。

当前保持 HSI，并未启用 PLL。原因是先完成最小工程，板上外部晶振型号和频率还未核对，使用内部时钟可以减少首次启动对板级信息的依赖。F103ZE 的最高工作频率为 72 MHz，这个能力不会使程序自动运行在 72 MHz。

当前代码的含义：

```c
RCC_OscInitStruct.PLL.PLLState = RCC_PLL_NONE;          // 本配置不使用 PLL
RCC_ClkInitStruct.SYSCLKSource = RCC_SYSCLKSOURCE_HSI;  // 系统时钟源为 HSI
RCC_ClkInitStruct.AHBCLKDivider = RCC_SYSCLK_DIV1;      // AHB 不分频
RCC_ClkInitStruct.APB1CLKDivider = RCC_HCLK_DIV1;        // APB1 不分频
RCC_ClkInitStruct.APB2CLKDivider = RCC_HCLK_DIV1;        // APB2 不分频
```

因此当前标称 SYSCLK、HCLK、PCLK1、PCLK2 均为 8 MHz。AHB、APB 是内部总线，对应不同内核/外设模块的时钟分配。后续定时器、UART、ADC、CAN 的时序参数都要基于实际时钟计算；CAN 阶段再结合速率和时钟精度确认方案。

验证：查看 main.c 的 SystemClock_Config 与 CubeMX 的 Clock Configuration，确认 HSI 为系统时钟源、总线频率为 8 MHz。尚未实测振荡器频率。

### 最小工程当时保留的默认项与代码保护区域

这些不是本轮新要求修改的设置，用来帮助理解生成结果：

### 四空格缩进与格式化

Tab键是输入动作，Tab字符与普通空格是不同字符。editor.insertSpaces=true时，按Tab键插入空格；tabSize=4决定插入宽度。已有两空格不会因为改设置自动变成四空格。

CubeMX生成器采用自己的格式；VS Code设置不会改变CubeMX的模板。约定：以后手写C代码、用户区和新增模块采用四空格，自动生成部分保留生成器格式。缩进宽度不改变这些C语句由大括号确定的层级。

在仓库根目录新建.vscode/settings.json，内容如下；如果文件已有内容，则合并设置：

```json
{
    "editor.insertSpaces": true,
    "editor.tabSize": 4,
    "editor.detectIndentation": false,
    "[c]": {
        "editor.defaultFormatter": "ms-vscode.cpptools",
        "editor.formatOnSave": false
    },
    "C_Cpp.clang_format_style": "{ BasedOnStyle: LLVM, IndentWidth: 4, UseTab: Never, BreakBeforeBraces: Allman }"
}
```

各项作用：

| 设置 | 作用 |
| --- | --- |
| editor.insertSpaces | 用普通空格进行缩进 |
| editor.tabSize | 每级四空格 |
| editor.detectIndentation=false | 不让旧文件的两空格布局覆盖所选宽度 |
| editor.defaultFormatter | C文件使用Microsoft C/C++扩展格式化 |
| editor.formatOnSave=false | 保存时不自动重排整份main.c |
| C_Cpp.clang_format_style | 手动格式化采用四空格、禁止Tab字符及另起一行的大括号 |

初次检查时main.c里Error_Handler分支等用户代码有缩进未对齐，逻辑仍由大括号决定。需要整理时只选用户代码块，按Ctrl+K再Ctrl+F执行Format Selection；不要批量格式化整个HAL/CMSIS库。自动生成部分整体改成四空格后，再生成还会回到生成器的格式，造成反复的无关diff。

后续助手直接提供的C示例使用四空格。已有历史教程与生成代码不追溯批量改写。

### 为什么用 Git 同步

Git 在本机保存提交历史，可以比较修改和恢复之前的版本。GitHub 托管远端 Git 仓库，方便备份、展示与协作。

基本流程为：修改工作区文件 → git add 暂存本次内容 → git commit 保存本地版本 → git push 发送到 GitHub。保存文件不会自动上传；commit 也只发生在本机，push 才更新远端。

本项目在 D:\嵌入式学习\电池管理系统 根目录管理一个仓库，将文档、CubeMX 配置和 MCU 工程一起记录，而非仅管理 main.c。

| --- | --- |
| README.md、docs、项目截图 | 提交，保存需求、进展与实际证据 |
| .gitignore、.gitattributes | 提交，共享忽略规则和文本换行规则 |
| .ioc | 提交，可复现 CubeMX 配置 |
| Core、必要 Drivers | 提交，包含当前构建所用源码与头文件 |
| .uvprojx、.uvoptx、启动汇编 | 提交，保留构建、调试选项和启动代码 |

### 本次唯一目标

为电压、电流、温度建立共用的数据格式，将头文件包含到当前 Keil 工程并编译通过。暂不实现 ADC、CAN、保护判断和状态机；本轮没有硬件接线。

采样任务以后提供这些数据，保护模块读取它们，CAN 模块按协议编码它们。先统一格式，可以减少后续各模块对单位、有效性和更新时间的不同理解。

### 第一步：新建 bms_types.h

在当前工程 Core/Inc 下新建 bms_types.h，即：

```text
D:\嵌入式学习\电池管理系统\MCU\projects\bms_bringup\Core\Inc\bms_types.h
```

写入以下内容：

```c
#ifndef BMS_TYPES_H
#define BMS_TYPES_H

#include <stdint.h>

#define BMS_CELL_COUNT 3u

typedef enum
{
    BMS_SOURCE_NONE = 0,
    BMS_SOURCE_SIMULATED,
    BMS_SOURCE_ADC,
    BMS_SOURCE_AFE
} BmsSampleSource;

typedef struct
{
    int32_t value;
    uint32_t timestamp_ms;
    uint8_t valid;
    BmsSampleSource source;
} BmsMeasurement;

typedef struct
{
    BmsMeasurement cell_mv[BMS_CELL_COUNT];
    BmsMeasurement current_ma;
    BmsMeasurement temperature_dC;
} BmsSample;

#endif
```

#### 为什么这样写

| 内容 | 含义与原因 |
| --- | --- |
| #ifndef / #define / #endif | 头文件保护，防止同一编译单元重复包含后重复定义类型 |
| stdint.h | 提供 int32_t、uint32_t、uint8_t 等明确位宽的整数类型 |
| BMS_CELL_COUNT 3u | 当前默认 3 串，用一个宏统一数组长度；u 表示无符号整数字面量 |
| typedef enum | 定义一组有名称的来源值，并将类型命名为 BmsSampleSource |
| typedef struct | 将相关字段组织成一份数据，并提供 BmsMeasurement 或 BmsSample 类型名 |
| 嵌套结构体 | 每一路测量都带自己的数值、时间、有效性和来源，多个测量组成一个采样快照 |

来源字段的含义：NONE 表示未取得数据；SIMULATED 表示软件构造的数据；ADC 表示经 MCU ADC 获取；AFE 表示经电池采样前端获取。声明这些名称不等于已经实现对应驱动。ADC 只说明采集路径，电位器模拟电池电压的实验仍必须在文档中标为模拟输入。

#### 每个测量字段的作用

- value：当前测量值。第一版统一使用 int32_t，方便表示有符号电流、负温度，并减少初次练习中的类型差异；有效电压仍要求非负，具体范围检查后续加入。
- timestamp_ms：取得新采样时的毫秒时间，后续可以使用 HAL_GetTick。它表示 MCU 启动后的时间计数，并非年月日。CAN 重复上报旧值时不能刷新该字段。
- valid：0 表示不可用于正常测量判断，1 表示已通过当前采集及有效性检查。有效性和新鲜度分别判断，valid=1 仍可能因时间过旧而超时。
- source：保留数据来源，便于演示时区分软件构造数据、ADC 输入和 AFE 数据。

每个单体电压、总电流、温度均拥有这些字段，以适应不同刷新节奏。不能因温度更新了，就把旧电压的时间也更新。

#### 数值单位约定

| 字段 | 单位与示例 |
| --- | --- |
| cell_mv[0].value | 第 1 节单体电压，单位 mV；3700 表示 3.700 V |
| current_ma.value | 电流，单位 mA；本练习约定正数为放电、负数为充电，接真实采样后需校验方向 |
| temperature_dC.value | 温度，单位 0.1℃；250 表示 25.0℃，-50 表示 -5.0℃ |

统一整数单位便于后续阈值比较和 CAN 编码。数组下标从 0 开始，三节对应 cell_mv[0]、cell_mv[1]、cell_mv[2]。

这里只定义类型，没有创建 BmsSample 变量，也没有初始化或获取任何测量值。以后创建 BmsSample sample = {0} 时，valid 和 source 的零值将表示尚未取得有效数据，不能把 value=0 当作一次真实零电压采样。

## 单体过压与采样超时

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

本章的测试示例和验收方法统一收录于[测试记录](测试记录.md#t08)。

### 已实现的内容

当前实现位于 [bms_protection.h](../MCU/projects/bms_bringup/Core/Inc/bms_protection.h) 和 [bms_protection.c](../MCU/projects/bms_bringup/Core/Src/bms_protection.c)，依赖 [bms_types.h](../MCU/projects/bms_bringup/Core/Inc/bms_types.h)。

| 函数 | 检查内容 | 返回结果 |
| --- | --- | --- |
| Bms_CheckCellOverVoltage | 单路电压的基本有效性与过压阈值 | 数据无效、未触发过压、触发过压 |
| Bms_CheckSampleFreshness | 单路测量的标志、来源及更新时间 | 数据或参数无效、未超时、超时 |

过压检查中，空指针、valid 不为 1、来源为 NONE、负电压、非正阈值均返回无效；有效电压达到阈值就触发过压。

时效检查中，空指针、valid 不为 1、来源为 NONE、max_age_ms 为 0 均返回无效。数据年龄通过无符号减法计算，达到允许的最大年龄就判超时。单独通过时效检查不代表数值正常，单独未触发过压也不代表数据没有过期。

当前来源检查只排除 NONE；采样驱动尚未实现，valid 标志由测试构造。后续驱动的实际有效性检查需另行验证。

### 时间戳的约定

- timestamp_ms 记录取得新采样时的毫秒计数。
- now_ms 与 timestamp_ms 必须来自同一个计数器；未来可统一使用 HAL_GetTick()。
- 采样先于检查，实际间隔小于一个完整的 32 位毫秒计数周期，约 49.7 天。
- 计数回绕后仍通过无符号减法计算年龄，不能简单用当前计数是否更大判断。
- timestamp_ms 为 0 可以表示启动时刻；是否有采样依靠有效标志和来源判断。
- 重复打印或 CAN 上报旧值时，不刷新采样时间戳。

4200 mV、500 ms 都是软件测试参数，尚未冻结实物电池的保护阈值或各通道超时值。

### 为什么使用三个位图

每节电池需要保留故障位置，而整组可能同时发生多个问题。一个字节的不同位可以分别表示不同单体：

| 位图值 | 低三位 | 对应单体 |
| --- | --- | --- |
| 0x00 | 000 | 没有记录这类问题 |
| 0x01 | 001 | 第 1 节 |
| 0x02 | 010 | 第 2 节 |
| 0x04 | 100 | 第 3 节 |
| 0x05 | 101 | 第 1、3 节 |
| 0x07 | 111 | 第 1、2、3 节 |

从右往左，最低位是 bit0。数组下标 0、1、2 分别对应 bit0、bit1、bit2。

分别使用 over_voltage_mask、invalid_mask、timeout_mask，便于后续日志和 CAN 同时表达故障类型与位置。每个位图当前使用 uint8_t，最多表示 8 节；本项目宏为 3，计划的 5 串也在这一范围内。若将来超过 8 节，必须修改位图类型和测试。

额外的 input_error 用于整组指针或参数错误。此时三个位图为零仍不能视为检查正常，调用者必须检查所有四个字段。

### 第一步：在 bms_protection.h 添加类型和声明

打开 [bms_protection.h](../MCU/projects/bms_bringup/Core/Inc/bms_protection.h)，保留已有内容，将下方代码放在最后的 #endif 之前：

```c
/*
 * 三节单体电压的检查汇总。
 * 三个位图均约定：bit0 对应第1节，bit1 对应第2节，bit2 对应第3节。
 * 对应位为 1，表示该节存在这一类问题。uint8_t 最多容纳 8 节。
 */
typedef struct
{
    uint8_t over_voltage_mask; /* 有效且未超时的数据中，哪些单体达到过压阈值 */
    uint8_t invalid_mask;      /* 哪些单体没有可用数据，或电压数值不合理 */
    uint8_t timeout_mask;      /* 哪些单体的数据已经超时 */
    uint8_t input_error;       /* 1：整组指针或检查参数错误；0：参数检查通过 */
} BmsVoltageReport;

/*
 * 汇总单体电压的过压、无效和超时情况。
 * sample：整组采样快照；这里只读取 cell_mv 数组。
 * ov_threshold_mv：单体过压阈值，单位 mV，必须大于 0。
 * now_ms、max_age_ms：与前面的时效检查使用相同含义。
 * 返回值是本次检查结果；这里不保存故障历史，也不控制负载。
 */
BmsVoltageReport Bms_CheckPackVoltages(
    const BmsSample *sample,
    int32_t ov_threshold_mv,
    uint32_t now_ms,
    uint32_t max_age_ms);
```

BmsVoltageReport 是一个结构体，四个字段作为一个整体返回，不需要动态申请内存。此结构体表示本次检查结果，不记录过去的故障。

### 第二步：在 bms_protection.c 添加实现

打开 [bms_protection.c](../MCU/projects/bms_bringup/Core/Src/bms_protection.c)，将下面函数追加到现有函数后面。文件顶部已经包含 bms_protection.h 和 stddef.h，后者提供 NULL。

```c
BmsVoltageReport Bms_CheckPackVoltages(
    const BmsSample *sample,
    int32_t ov_threshold_mv,
    uint32_t now_ms,
    uint32_t max_age_ms)
{
    /* 每次从全零结果开始，避免把上一次检查结果带进来。 */
    BmsVoltageReport report = {0};
    uint32_t i;
    uint8_t cell_bit;
    const BmsMeasurement *cell;
    BmsSampleStatus sample_status;
    BmsOvResult ov_result;

    /* 参数错误单独报告，调用者必须同时检查 input_error。 */
    if (sample == NULL || ov_threshold_mv <= 0 || max_age_ms == 0u)
    {
        report.input_error = 1u;
        return report;
    }

    for (i = 0u; i < BMS_CELL_COUNT; i++)
    {
        cell = &sample->cell_mv[i];

        /* i 为 0、1、2 时，分别得到二进制 001、010、100。 */
        cell_bit = (uint8_t)(1u << i);

        /* 先确认这一路数据可用且没有过期。 */
        sample_status = Bms_CheckSampleFreshness(cell, now_ms, max_age_ms);

        if (sample_status == BMS_SAMPLE_INVALID)
        {
            report.invalid_mask |= cell_bit;
            continue; /* 这一节不能继续检查，转到下一节。 */
        }

        if (sample_status == BMS_SAMPLE_TIMEOUT)
        {
            report.timeout_mask |= cell_bit;
            continue; /* 旧数据不用于报告当前过压。 */
        }

        /* 只有通过时效检查的数据，才继续检查电压数值。 */
        ov_result = Bms_CheckCellOverVoltage(cell, ov_threshold_mv);

        if (ov_result == BMS_OV_DATA_INVALID)
        {
            report.invalid_mask |= cell_bit;
        }
        else if (ov_result == BMS_OV_TRIGGERED)
        {
            /* 按位或可以保留前面已经记录的其他单体。 */
            report.over_voltage_mask |= cell_bit;
        }
    }

    return report;
}
```

关键语句的含义：

| 语句或表达式 | 含义 |
| --- | --- |
| report = {0} | 创建本次结果，并将所有字段初始化为零 |
| &sample->cell_mv[i] | 取得第 i 个单体测量对象的地址，交给已有函数读取 |
| 1u << i | 将最低位的 1 左移 i 位，得到本节对应的位置 |
| mask |= cell_bit | 把本节对应位置为 1，同时保留其他单体已经置位的结果 |
| continue | 本节已记录无效或超时，直接检查下一节 |
| return report | 返回整份检查结果，由调用者决定如何记录或处理 |

检查顺序是：整组参数 → 单路标志与来源 → 单路超时 → 电压数值与过压。

同一节本次按此顺序归入一类结果。例如，旧数据即使是 4300 mV，也只报告超时；全零快照因 valid=0 和 source=NONE 报告无效。不同节的问题可以同时记录，不能发现第一处问题就提前结束循环。

这是当前快照的分类规则，后续状态机中的故障历史和锁存需要单独维护。

### 本步能够说明的设计

通过本步，可以解释为什么要复用单路检查、为什么数据无效与超时需要单独报告、为什么要保留故障位置，以及为什么本次检查结果与历史故障锁定应分开。

本页初版报告只有四个字段；[电压上下限汇总](开发步骤.md#s12) 已增加第五个字段 under_voltage_mask。所有字段为零仅说明通过本项电压检查；其他保护及状态机的最新进度见 [项目入口](../README.md#当前推进点)。

### 第二步：添加函数实现

打开 [bms_protection.c](../MCU/projects/bms_bringup/Core/Src/bms_protection.c)，在已有函数后面添加。文件顶部已经包含提供 NULL 的 stddef.h。

```c
BmsUvResult Bms_CheckCellUnderVoltage(
    const BmsMeasurement *cell,
    int32_t threshold_mv)
{
    /*
     * 先检查指针，再访问对象成员。
     * valid 不为 1 或没有来源的数据，不能用于正常电压判断。
     */
    if (cell == NULL ||
        cell->valid != 1u ||
        cell->source == BMS_SOURCE_NONE)
    {
        return BMS_UV_DATA_INVALID;
    }

    /* 负电压和非正数阈值不符合本函数的输入约定。 */
    if (cell->value < 0 || threshold_mv <= 0)
    {
        return BMS_UV_DATA_INVALID;
    }

    /*
     * 本项目约定：达到或低于欠压阈值，就触发欠压。
     * value 为 0 且标志有效时，也应触发，不能写成 value <= 0 判无效。
     */
    if (cell->value <= threshold_mv)
    {
        return BMS_UV_TRIGGERED;
    }

    return BMS_UV_NOT_TRIGGERED;
}
```

过压使用 value >= threshold_mv，欠压使用 value <= threshold_mv。当前两种检查都约定包含相等的边界。

本函数只检查基本标志、来源、数值与阈值，不判断时间戳；组合使用时仍需先检查数据是否过期。暂不增加滞回、持续时间判定或故障锁存，这些属于后续组合保护与状态机的实现。

### 第三步：替换汇总函数实现

在 Core/Src/bms_protection.c 中，完整替换原 Bms_CheckPackVoltages，保留另外三个单路函数：

```c
BmsVoltageReport Bms_CheckPackVoltages(
    const BmsSample *sample,
    int32_t uv_threshold_mv,
    int32_t ov_threshold_mv,
    uint32_t now_ms,
    uint32_t max_age_ms)
{
    BmsVoltageReport report = {0};
    uint32_t i;
    uint8_t cell_bit;
    const BmsMeasurement *cell;
    BmsSampleStatus sample_status;
    BmsOvResult ov_result;
    BmsUvResult uv_result;

    /*
     * 下限必须大于0，上限必须高于下限。
     * 上下限相等或顺序颠倒时，不能继续做正常保护判断。
     */
    if (sample == NULL ||
        uv_threshold_mv <= 0 ||
        ov_threshold_mv <= uv_threshold_mv ||
        max_age_ms == 0u)
    {
        report.input_error = 1u;
        return report;
    }

    for (i = 0u; i < BMS_CELL_COUNT; i++)
    {
        cell = &sample->cell_mv[i];
        cell_bit = (uint8_t)(1u << i);

        /* 先检查标志、来源和时间，旧数据不用于报告当前过压或欠压。 */
        sample_status = Bms_CheckSampleFreshness(
            cell, now_ms, max_age_ms);

        if (sample_status == BMS_SAMPLE_INVALID)
        {
            report.invalid_mask |= cell_bit;
            continue;
        }

        if (sample_status == BMS_SAMPLE_TIMEOUT)
        {
            report.timeout_mask |= cell_bit;
            continue;
        }

        /* 复用两个单节函数，不在汇总函数中重复实现阈值比较。 */
        ov_result = Bms_CheckCellOverVoltage(cell, ov_threshold_mv);
        uv_result = Bms_CheckCellUnderVoltage(cell, uv_threshold_mv);

        if (ov_result == BMS_OV_DATA_INVALID ||
            uv_result == BMS_UV_DATA_INVALID)
        {
            report.invalid_mask |= cell_bit;
        }
        else if (ov_result == BMS_OV_TRIGGERED)
        {
            report.over_voltage_mask |= cell_bit;
        }
        else if (uv_result == BMS_UV_TRIGGERED)
        {
            report.under_voltage_mask |= cell_bit;
        }
    }

    return report;
}
```

检查顺序为：整组参数 → 单路数据标志和来源 → 单路时效 → 电压数值和上下限。

参数不合理时单独设置 input_error。有效且未超时的数据才会进入过压与欠压判断；负电压返回无效，标记有效的零电压触发欠压。

上下限必须严格有序。这样同一节有效电压不可能同时达到过压和欠压条件，分支可以按过压、欠压顺序分类。不同节可以分别出现不同问题。

报告每次从零构造，表示本次快照结果；历史故障锁存仍由后续状态机负责。

```c
BmsTemperatureResult Bms_CheckTemperature(
    const BmsMeasurement *temperature,
    int32_t over_temp_dC,
    uint32_t now_ms,
    uint32_t max_age_ms)
{

    /* 先区分调用参数错误与测量数据本身无效。 */
    if (temperature == NULL || max_age_ms == 0u)
    {
        return BMS_TEMP_INPUT_ERROR;
    }

    /* 复用时效检查，避免每种保护都重写时间差计算。 */

    if (sample_status == BMS_SAMPLE_INVALID)
```

### 第二步：添加实现

在 Core/Src/bms_protection.c 的现有函数后添加：

```c
BmsCurrentResult Bms_CheckCurrent(
    const BmsMeasurement *current,
    int32_t discharge_limit_ma,
    int32_t charge_limit_ma,
    uint32_t now_ms,
    uint32_t max_age_ms)
{
    BmsSampleStatus sample_status;

    /* 两个方向的限值都必须是正数，方向由电流值的正负表示。 */
    if (current == NULL ||
        discharge_limit_ma <= 0 ||
        charge_limit_ma <= 0 ||
        max_age_ms == 0u)
    {
        return BMS_CURRENT_INPUT_ERROR;
    }

    sample_status = Bms_CheckSampleFreshness(
        current, now_ms, max_age_ms);

    if (sample_status == BMS_SAMPLE_INVALID)
    {
        return BMS_CURRENT_DATA_INVALID;
    }

    if (sample_status == BMS_SAMPLE_TIMEOUT)
    {
        /* 旧电流不用于报告当前是否过流。 */
        return BMS_CURRENT_TIMEOUT;
    }

    /* 正方向达到限值，触发放电过流。 */
    if (current->value >= discharge_limit_ma)
    {
        return BMS_CURRENT_DISCHARGE_OVER_LIMIT;
    }

    /*
     * 将正数的充电限值变为负边界，再直接比较。
     * 不对测量值取绝对值，避免 INT32_MIN 取负时溢出。
     * charge_limit_ma 已确认是正数，因此对它取负可以安全表示。
     */
    if (current->value <= -charge_limit_ma)
    {
        return BMS_CURRENT_CHARGE_OVER_LIMIT;
    }

    return BMS_CURRENT_NORMAL;
}
```

检查顺序仍为参数、标志与来源、时间、数值边界。过期的正负大电流均先报告超时，保留实际问题类型。

INT32_MIN 的值为 -2147483648，取正后的 2147483648 超出 int32_t 范围。因此这里直接比较负边界，不对测量值取绝对值。charge_limit_ma 已经检查为正数，对它取负在 int32_t 中可以表示。

只有 BMS_CURRENT_NORMAL 表示本项通过。即使电流结果正常，仍需结合电压、温度以及后续状态机决定系统行为。

## 统一故障位图

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

本章的测试示例和验收方法统一收录于[测试记录](测试记录.md#t15)。

### 本步目标与调用关系

把 Bms_CheckPackVoltages()、Bms_CheckTemperature() 和 Bms_CheckCurrent() 的返回结果交给 Bms_CombineFaults()，得到 uint32_t 故障位图。后续状态机再读取该位图决定是否允许运行。

每轮必须先完成三类检查，再汇总同一轮结果。不能只把电压报告清零、手填两个 NORMAL，就当作采样通过；本函数只转换已知结果，不重新检查原始采样和时间戳。

| 故障位 | 含义 | 十六进制值 |
| --- | --- | --- |
| bit0 | 至少一节过压 | 0x01 |
| bit1 | 至少一节欠压 | 0x02 |
| bit2 | 过温 | 0x04 |
| bit3 | 放电过流 | 0x08 |
| bit4 | 充电过流 | 0x10 |
| bit5 | 至少一路数据无效 | 0x20 |
| bit6 | 至少一路数据超时 | 0x40 |
| bit7 | 输入参数或结果类型错误 | 0x80 |

原电压报告的位表示“哪节电池”；新故障位图的位表示“哪类故障”。例如第3节过压：原 over_voltage_mask 为 0x04，汇总后 CELL_OV 为 0x01。仍需保留原电压报告用于定位单体；总位图不记录无效或超时的具体通道。

0 表示本次已执行的检查没有发现故障，不等于完成全系统自检，也不意味着可以绕过状态机开启负载。该函数不保留历史；故障锁定、清除条件与命令留到状态机实现。位号是当前软件约定，CAN 报文格式尚未冻结。

### 第一步：增加故障类型和声明

在 Core/Inc/bms_protection.h 最后的 #endif 前添加，放在现有温度、电流类型定义之后：

```c
/*
 * 每一位代表一种故障，可以同时记录多种故障。
 * 注意：这里的位表示故障类型，不表示第几节电池。
 */
typedef enum
{
    BMS_FAULT_NONE           = 0u,       /* 本次没有发现已检查的故障 */
    BMS_FAULT_CELL_OV        = 1u << 0,  /* 单体过压 */
    BMS_FAULT_CELL_UV        = 1u << 1,  /* 单体欠压 */
    BMS_FAULT_OVER_TEMP      = 1u << 2,  /* 过温 */
    BMS_FAULT_DISCHARGE_OC   = 1u << 3,  /* 放电过流 */
    BMS_FAULT_CHARGE_OC      = 1u << 4,  /* 充电过流 */
    BMS_FAULT_DATA_INVALID   = 1u << 5,  /* 至少一路数据无效 */
    BMS_FAULT_SAMPLE_TIMEOUT = 1u << 6,  /* 至少一路数据超时 */
    BMS_FAULT_INPUT_ERROR    = 1u << 7   /* 检查参数或结果类型错误 */
} BmsFaultFlag;

/*
 * 汇总已经得到的电压、温度和电流检查结果。
 * 返回值是故障位图，使用 uint32_t 保存多个故障位。
 * 只描述本次结果；历史故障的锁定由后续状态机负责。
 */
uint32_t Bms_CombineFaults(
    const BmsVoltageReport *voltage,
    BmsTemperatureResult temperature_result,
    BmsCurrentResult current_result);
```

1u << n 把无符号整数 1 左移 n 位，使每个故障拥有不同的二进制位。BmsFaultFlag 用于命名单个位，组合后的值使用 uint32_t 保存。

### 第二步：添加汇总函数

在 Core/Src/bms_protection.c 的现有函数后添加。该文件已有 NULL 所需的标准头文件：

```c
uint32_t Bms_CombineFaults(
    const BmsVoltageReport *voltage,
    BmsTemperatureResult temperature_result,
    BmsCurrentResult current_result)
{
    /* 每次从零开始，避免上次结果混入本次检查。 */
    uint32_t faults = BMS_FAULT_NONE;

    if (voltage == NULL)
    {
        faults |= BMS_FAULT_INPUT_ERROR;
        /* 仍继续汇总温度和电流，保留其他已知故障。 */
    }
    else
    {
        /* 独立判断各字段，因为不同电池可能同时存在不同问题。 */
        if (voltage->over_voltage_mask != 0u)
        {
            faults |= BMS_FAULT_CELL_OV;
        }

        if (voltage->under_voltage_mask != 0u)
        {
            faults |= BMS_FAULT_CELL_UV;
        }

        if (voltage->invalid_mask != 0u)
        {
            faults |= BMS_FAULT_DATA_INVALID;
        }

        if (voltage->timeout_mask != 0u)
        {
            faults |= BMS_FAULT_SAMPLE_TIMEOUT;
        }

        if (voltage->input_error != 0u)
        {
            faults |= BMS_FAULT_INPUT_ERROR;
        }
    }

    switch (temperature_result)
    {
        case BMS_TEMP_NORMAL:
            break;

        case BMS_TEMP_OVER_LIMIT:
            faults |= BMS_FAULT_OVER_TEMP;
            break;

        case BMS_TEMP_DATA_INVALID:
            faults |= BMS_FAULT_DATA_INVALID;
            break;

        case BMS_TEMP_TIMEOUT:
            faults |= BMS_FAULT_SAMPLE_TIMEOUT;
            break;

        case BMS_TEMP_INPUT_ERROR:
        default:
            /* 未定义的枚举值也作为输入错误，不能当作正常。 */
            faults |= BMS_FAULT_INPUT_ERROR;
            break;
    }

    switch (current_result)
    {
        case BMS_CURRENT_NORMAL:
            break;

        case BMS_CURRENT_DISCHARGE_OVER_LIMIT:
            faults |= BMS_FAULT_DISCHARGE_OC;
            break;

        case BMS_CURRENT_CHARGE_OVER_LIMIT:
            faults |= BMS_FAULT_CHARGE_OC;
            break;

        case BMS_CURRENT_DATA_INVALID:
            faults |= BMS_FAULT_DATA_INVALID;
            break;

        case BMS_CURRENT_TIMEOUT:
            faults |= BMS_FAULT_SAMPLE_TIMEOUT;
            break;

        case BMS_CURRENT_INPUT_ERROR:
        default:
            faults |= BMS_FAULT_INPUT_ERROR;
            break;
    }

    return faults;
}
```

faults |= flag 等价于 faults = faults | flag，增加故障位并保留已经发现的其他故障。电压字段使用独立的 if，因为不同单体可以同时出现不同问题；温度和电流分别用 switch 映射单个结果。

电压报告为空时先记录输入错误，继续收集另外两类结果，避免漏掉已知故障。default 接住未定义的枚举值，将其报告为输入错误。

判断“是否存在过温”，使用 (faults & BMS_FAULT_OVER_TEMP) != 0u。只有判断“是否全部无故障”才使用 faults == BMS_FAULT_NONE；faults == BMS_FAULT_OVER_TEMP 会漏掉过温与其他故障并存的情况。

## 四状态机与故障锁定

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

### 本步范围与接口约定

状态机回答的是：当前处于什么阶段、能否启动、是否需要锁定，以及是否允许负载工作。保护模块回答的是：本轮检查发现什么故障。两者职责不同，状态机不重新比较测量阈值。

| 状态 | 作用 | load_enabled |
| --- | --- | --- |
| SELF_TEST | 等待自检通过 | 0 |
| STANDBY | 等待新的启动指令 | 0 |
| RUN | 允许运行，持续检查故障 | 1 |
| FAULT_LOCK | 记录故障，等待满足条件后清除 | 0 |

| 条件 | 转换 |
| --- | --- |
| 任一活动故障，不论当前状态及指令 | FAULT_LOCK，并累计故障 |
| SELF_TEST，自检通过且无故障 | STANDBY |
| STANDBY，新的 START、自检通过且无故障 | RUN |
| RUN，STOP 且无故障 | STANDBY |
| FAULT_LOCK，仅数值恢复 | 继续锁定 |
| FAULT_LOCK，CLEAR、自检通过、恢复许可为1且无活动故障 | STANDBY，清除锁定记录 |

本轮活动故障优先于指令；每轮最多执行一次状态转换。自检通过的同一轮即使收到 START，也只进入待机；CLEAR 只回待机，另发一次 START 才启动。

本步只实现基本转换与锁定。self_test_passed 由后续自检模块提供，clear_allowed 由后续恢复条件模块提供；测试先手动填写这两个标志。真实自检内容、启动等待期限、恢复回差和暂定 2 s 稳定时间尚未实现，不能把 clear_allowed 固定为1用于真实控制。

self_test_passed 是启动自检结论；运行期健康异常须通过 active_faults 报告。当前数据有效性与新鲜度由已有检查函数负责，每轮完成检查并汇总后再交给状态机，不能以未检查的零故障值代替真实结果。

load_enabled 是软件输出许可，并非已经驱动 GPIO，也不代表检测到了实际负载状态。后续控制模块会将许可映射为默认关闭的硬件输出。

### 第一步：新建状态机头文件

新建 Core/Inc/bms_state_machine.h：

```c
#ifndef BMS_STATE_MACHINE_H
#define BMS_STATE_MACHINE_H

#include "bms_protection.h"

/* 当前控制阶段；上电初始化后先进入自检。 */
typedef enum
{
    BMS_STATE_SELF_TEST = 0, /* 等待自检通过，负载关闭 */
    BMS_STATE_STANDBY,       /* 已准备好，等待启动指令 */
    BMS_STATE_RUN,           /* 允许运行 */
    BMS_STATE_FAULT_LOCK     /* 故障锁定，等待满足条件后清除 */
} BmsState;

/* 每次处理一个指令；没有新指令时填写 NONE。 */
typedef enum
{
    BMS_CMD_NONE = 0,
    BMS_CMD_START,
    BMS_CMD_STOP,
    BMS_CMD_CLEAR
} BmsCommand;

/* 状态机保存的运行记录，需要在多次调用之间保留。 */
typedef struct
{
    BmsState state;
    uint32_t latched_faults; /* 锁定期间累计出现过的故障 */
    uint8_t load_enabled;   /* 1：软件允许负载工作；尚未操作 GPIO */
} BmsStateMachine;

/* 本轮输入；测量检查和恢复条件检查由外部提供。 */
typedef struct
{
    uint32_t active_faults;   /* 本轮 Bms_CombineFaults() 的结果 */
    BmsCommand command;      /* 本轮新收到的指令 */
    uint8_t self_test_passed; /* 1：自检已通过；0：尚未通过 */
    uint8_t clear_allowed;    /* 1：恢复条件已满足；0：禁止清除 */
} BmsControlInput;

/* 上电时调用一次，或测试中模拟复位时调用。 */
void Bms_StateMachineInit(BmsStateMachine *machine);

/*
 * 周期调用，即使没有指令也要检查故障。
 * 本函数只更新状态和输出许可，不操作真实负载。
 */
void Bms_StateMachineStep(
    BmsStateMachine *machine,
    const BmsControlInput *input);

#endif
```

BmsStateMachine 保存跨多轮保留的状态；BmsControlInput 保存本轮输入，两者不要混在一起。每轮活动故障可以消失，但锁定故障只有 CLEAR 成功或重新初始化才会清零。

command 表示一次新指令。调用方应消费后将下一轮指令设为 NONE，只有收到另一条指令时才重新填写；状态机不自行保存或排队，CAN 命令解析和队列留待后续实现。

### 第二步：新建状态机源文件

新建 Core/Src/bms_state_machine.c：

```c
#include <stddef.h>
#include "bms_state_machine.h"

void Bms_StateMachineInit(BmsStateMachine *machine)
{
    if (machine == NULL)
    {
        return;
    }

    machine->state = BMS_STATE_SELF_TEST;
    machine->latched_faults = BMS_FAULT_NONE;
    machine->load_enabled = 0u;
}

void Bms_StateMachineStep(
    BmsStateMachine *machine,
    const BmsControlInput *input)
{
    if (machine == NULL)
    {
        return;
    }

    /* 先关闭软件许可，只有最后确认处于 RUN 才重新置为1。 */
    machine->load_enabled = 0u;

    if (input == NULL)
    {
        machine->state = BMS_STATE_FAULT_LOCK;
        machine->latched_faults |= BMS_FAULT_INPUT_ERROR;
        return;
    }

    /* 故障优先于所有指令，包括 STOP 和 CLEAR。 */
    if (input->active_faults != BMS_FAULT_NONE)
    {
        machine->state = BMS_STATE_FAULT_LOCK;

        /* 累计故障，不覆盖锁定期间已经记录的其他故障。 */
        machine->latched_faults |= input->active_faults;
        return;
    }

    switch (machine->state)
    {
        case BMS_STATE_SELF_TEST:
            if (input->self_test_passed == 1u)
            {
                /* 本轮最多转到待机，不继续执行同一轮的 START。 */
                machine->state = BMS_STATE_STANDBY;
            }
            break;

        case BMS_STATE_STANDBY:
            if (input->command == BMS_CMD_START &&
                input->self_test_passed == 1u)
            {
                machine->state = BMS_STATE_RUN;
            }
            break;

        case BMS_STATE_RUN:
            if (input->command == BMS_CMD_STOP)
            {
                machine->state = BMS_STATE_STANDBY;
            }
            break;

        case BMS_STATE_FAULT_LOCK:
            /*
             * 到这里说明本轮没有活动故障。
             * 仍须收到 CLEAR、自检通过、恢复条件满足，才能解除锁定。
             */
            if (input->command == BMS_CMD_CLEAR &&
                input->self_test_passed == 1u &&
                input->clear_allowed == 1u)
            {
                machine->latched_faults = BMS_FAULT_NONE;
                machine->state = BMS_STATE_STANDBY;
            }
            break;

        default:
            /* 状态值不属于已定义的四种状态，关闭许可并锁定。 */
            machine->state = BMS_STATE_FAULT_LOCK;
            machine->latched_faults |= BMS_FAULT_INPUT_ERROR;
            break;
    }

    /* 输出许可由最终状态统一决定。 */
    if (machine->state == BMS_STATE_RUN)
    {
        machine->load_enabled = 1u;
    }
}
```

初始化函数只在上电时调用一次；测试可以再次调用来模拟复位。不要在主循环或每次 Step 前调用 Init，否则会清掉锁定记录。

Step 即使没有新指令也要周期执行，先接收最新保护结果，再处理指令。load_enabled 在函数入口被设为0，只有最后确认 RUN 才重新置为1；这只是变量更新，不代表函数内部已经执行了 GPIO 关闭。

输入指针为空或状态值异常会记录 INPUT_ERROR 并锁定。machine 指针为空则直接返回，无法更新任何状态；实际控制方必须始终持有有效的状态机对象，空指针返回不能当作真实硬件已关闭的证据。

## 恢复区间与稳定计时

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

本章的测试示例和验收方法统一收录于[测试记录](测试记录.md#t17)。

### 本步目标与边界

给状态机提供真正计算出来的 clear_allowed：本轮无活动故障，所有必需测量有效、新鲜且进入恢复区间，并持续达到设定时间，才返回1。任一条件不满足立即返回0并重置计时。这里复用已有检查函数，既检查数值，也检查基本有效标志、来源与时间戳。

“没有触发故障”与“满足恢复条件”使用不同边界。例如软件测试中单体达到4200 mV触发过压，但恢复要求小于4100 mV；4150 mV虽然不再触发过压，仍不能开始恢复计时。这一段阈值间隔构成恢复回差。

| 项目 | 原保护测试参数 | 本页恢复测试条件 |
| --- | --- | --- |
| 单体欠压 | ≤3000 mV触发 | 每节 >3200 mV |
| 单体过压 | ≥4200 mV触发 | 每节 <4100 mV |
| 过温 | ≥60.0℃触发 | <55.0℃ |
| 放电过流 | ≥1000 mA触发 | <800 mA |
| 充电过流 | ≤-500 mA触发 | >-300 mA |
| 数据时效 | 按通道检查 | 本页三类通道均 <500 ms |
| 稳定时间 | 尚未计算 | 连续满足恢复条件 ≥2000 ms |

这些都是软件测试配置，尚非实物电池的保护参数。本页恢复边界使用严格不等号，因为复用的检查函数在相等时报告达到阈值。温度低限保护不在本步实现。

恢复配置应位于正常保护边界以内；本独立模块没有接收正常保护的阈值配置，不能自动比较两组配置的关系。[统一控制周期](开发步骤.md#s18) 已实现两组配置的集中校验，并通过电脑测试。计时期间配置保持不变，修改配置须重新初始化恢复记录。

本模块不清除锁定、不处理指令、不操作 GPIO。返回1以后仍须由状态机同时检查 CLEAR、自检结论及活动故障；过早收到的 CLEAR 不缓存。

### 第一步：新建恢复头文件

新建 Core/Inc/bms_recovery.h：

```c
#include "bms_protection.h"

    int32_t cell_min_mv;         /* 每节电压必须严格大于此值 */
    int32_t cell_max_mv;         /* 每节电压必须严格小于此值 */

    uint32_t temperature_max_age_ms;

{

    uint8_t timing;              /* 1：正在累计稳定时间 */

/*
 * 在故障锁定期间周期调用。
 * active_faults 是本轮正常保护检查的结果。
 * 返回1只表示恢复许可成立，清除仍须交给状态机判断。
 */
```

timing 单独表示计时是否开始，不能用 stable_since_ms==0 代替，因为系统0 ms也可以开始计时。恢复记录跨多次调用保存，上电初始化一次，退出锁定后重新初始化。

### 第二步：新建恢复源文件

新建 Core/Src/bms_recovery.c：

```c
#include <stddef.h>
#include "bms_recovery.h"

void Bms_RecoveryInit(BmsRecovery *recovery)
{
    if (recovery == NULL)
    {
        return;
    }

    recovery->stable_since_ms = 0u;
    recovery->timing = 0u;
}

uint8_t Bms_RecoveryUpdate(
    BmsRecovery *recovery,
    const BmsSample *sample,
    const BmsRecoveryConfig *config,
    uint32_t active_faults,
    uint32_t now_ms)
{
    BmsVoltageReport voltage;
    BmsTemperatureResult temperature;
    BmsCurrentResult current;

    if (recovery == NULL)
    {
        return 0u;
    }

    if (sample == NULL || config == NULL ||
        active_faults != BMS_FAULT_NONE)
    {
        Bms_RecoveryInit(recovery);
        return 0u;
    }

    if (config->stable_time_ms == 0u)
    {
        Bms_RecoveryInit(recovery);
        return 0u;
    }

    /*
     * 复用已有检查函数，但传入更严格的恢复边界。
     * 它们也会检查参数、有效标志、来源和数据时效。
     */
    voltage = Bms_CheckPackVoltages(
        sample, config->cell_min_mv, config->cell_max_mv,
        now_ms, config->voltage_max_age_ms);

    temperature = Bms_CheckTemperature(
        &sample->temperature_dC, config->max_temperature_dC,
        now_ms, config->temperature_max_age_ms);

    current = Bms_CheckCurrent(
        &sample->current_ma,
        config->discharge_limit_ma, config->charge_limit_ma,
        now_ms, config->current_max_age_ms);

    /*
     * 此处汇总的是“是否满足恢复边界”，不用于替换活动故障。
     * 任一项不通过，就丢弃之前累计的稳定时间。
     */
    if (Bms_CombineFaults(&voltage, temperature, current)
        != BMS_FAULT_NONE)
    {
        Bms_RecoveryInit(recovery);
        return 0u;
    }

    if (recovery->timing != 1u)
    {
        recovery->stable_since_ms = now_ms;
        recovery->timing = 1u;
        return 0u;
    }

    /*
     * 使用无符号时间差处理毫秒计数回绕。
     * 必须使用同一时钟，并在一个完整计数周期内持续调用。
     */
    if ((uint32_t)(now_ms - recovery->stable_since_ms)
        >= config->stable_time_ms)
    {
        return 1u;
    }

    return 0u;
}
```

检查顺序为调用参数及活动故障、恢复配置与测量检查、启动计时、判断是否达到稳定时间。第一次满足恢复条件时只记录起点并返回0，没有等待循环，也没有 HAL_Delay()。

这里给已有保护检查函数传入恢复边界，内部结果仅用于判断“是否处于恢复区间”。不能把这些内部结果写回正常 active_faults，否则会混淆故障触发阈值与恢复阈值。传入的 active_faults 仍由正常保护检查获得。

现在减去起点的无符号时间差能处理一次计数回绕。now_ms 与采样时间戳必须来自同一个计时来源，实际累计间隔应小于 uint32_t 完整周期约49.7天；不支持跨多个完整周期推算时间。

稳定时间代表周期检查中持续观察到条件满足。必须周期运行控制检查，不允许人为刷新旧数据时间戳来维持有效；采样间隔内的瞬态和控制任务停滞，仍须依靠后续采样周期设计、任务监控及硬件保护处理。

### 第五步：加入 Keil 与后续调用规则

在 Keil 的 Application/User/Core 组右键 Add Existing Files to Group，添加 Core/Src/bms_recovery.c，可同时添加头文件。保存工程并构建，确认日志包含 compiling bms_recovery.c，最终为0错误、0警告。测试文件不加入 Keil。

本步先验证独立模块和电脑联合测试，main.c 暂不改动。统一控制周期将在下一步整合，调用顺序如下：

```text
取得本轮完整测量快照
    → 用正常保护阈值检查，得到 active_faults
    → 当前为 FAULT_LOCK：更新恢复模块，得到 clear_allowed
      其他状态：初始化恢复记录，并将 clear_allowed 设为0
    → 将活动故障、恢复许可、自检结论和新指令交给状态机
    → 消费本轮指令，下轮无新指令时填写 NONE
```

不能在正常运行阶段一直累计恢复时间，否则新故障刚消失时可能复用先前计时。没有新指令也要周期更新保护、恢复和状态机，不能只在收到 CLEAR 时才检查一次。

## 统一控制周期

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

本章的测试示例和验收方法统一收录于[测试记录](测试记录.md#t18)。

### 本步目标与执行顺序

新增 Bms_ControllerStep()，接收一轮完整采样、一条新指令、自检结论、配置与当前时间，按顺序执行：

```text
校验保护与恢复配置
    → 正常电压、温度、电流检查
    → 汇总本轮 active_faults
    → 故障锁定期间更新 clear_allowed
    → 状态机处理故障与指令
    → 得到最终状态、锁定故障和软件负载许可
```

其他状态不累计恢复时间，清除成功后立即重置计时。每一轮使用同一采样快照和同一 now_ms，模块不修改测量值或时间戳，也不保存指令。

本步补齐保护配置与恢复配置的关系校验，恢复边界必须位于正常区间内且保留回差。错误配置立即作为 INPUT_ERROR 交给状态机锁定，不能等故障发生后才发现恢复配置不合适。

同一次运行中保持配置不变。const 指针仅限制通过该指针修改，不自动防止外部改动；更改配置前须重新开始恢复计时。实际自检仍由外部提供，当前测试手动传入其结论。

### 第一步：新建控制头文件

新建 Core/Inc/bms_controller.h：

```c
#ifndef BMS_CONTROLLER_H
#define BMS_CONTROLLER_H

#include "bms_state_machine.h"
#include "bms_recovery.h"

/* 正常保护阈值与恢复配置放在一起，便于统一校验。 */
typedef struct
{
    int32_t uv_threshold_mv;       /* 单体欠压触发值，单位mV */
    int32_t ov_threshold_mv;       /* 单体过压触发值，单位mV */
    int32_t over_temp_dC;          /* 过温触发值，单位0.1℃ */
    int32_t discharge_limit_ma;    /* 放电限值，填写正数，单位mA */
    int32_t charge_limit_ma;       /* 充电限值大小，填写正数，单位mA */
    uint32_t voltage_max_age_ms;
    uint32_t temperature_max_age_ms;
    uint32_t current_max_age_ms;
    BmsRecoveryConfig recovery;
} BmsControllerConfig;

/* 需要跨控制周期保留的记录。 */
typedef struct
{
    BmsStateMachine machine;
    BmsRecovery recovery;
    uint32_t active_faults;  /* 本轮保护检查结果 */
    uint8_t clear_allowed;  /* 仅在故障锁定期间可能为1 */
} BmsController;

/* 上电调用一次，不要每轮重新初始化。 */
void Bms_ControllerInit(BmsController *controller);

/*
 * 处理一轮完整采样和一条新指令。
 * 无新指令时传入 NONE；本函数不保存指令，也不刷新采样时间戳。
 * 配置在运行期间保持不变；修改前须重新开始恢复计时。
 */
void Bms_ControllerStep(
    BmsController *controller,
    const BmsSample *sample,
    const BmsControllerConfig *config,
    BmsCommand command,
    uint8_t self_test_passed,
    uint32_t now_ms);

#endif
```

BmsController 保存跨多轮的记录，BmsControllerConfig 保存阈值与时效参数。初始 active_faults 标记为 DATA_INVALID，表示首次检查未执行；初始化状态仍为 SELF_TEST，负载许可为0，锁定历史为0。

### 第二步：新建控制源文件

新建 Core/Src/bms_controller.c：

```c
#include <stddef.h>
#include "bms_controller.h"

/* static表示这个辅助函数只在本文件内部使用。 */
static uint8_t Bms_ControllerConfigIsValid(
    const BmsControllerConfig *config)
{
    const BmsRecoveryConfig *recovery;

    if (config == NULL)
    {
        return 0u;
    }

    recovery = &config->recovery;

    /* 先检查正常保护参数是否成立。 */
    if (config->uv_threshold_mv <= 0 ||
        config->ov_threshold_mv <= config->uv_threshold_mv ||
        config->discharge_limit_ma <= 0 ||
        config->charge_limit_ma <= 0 ||
        config->voltage_max_age_ms == 0u ||
        config->temperature_max_age_ms == 0u ||
        config->current_max_age_ms == 0u)
    {
        return 0u;
    }

    /* 恢复边界必须位于正常区间内，保留明确的回差。 */
    if (recovery->cell_min_mv <= config->uv_threshold_mv ||
        recovery->cell_max_mv >= config->ov_threshold_mv ||
        recovery->cell_min_mv >= recovery->cell_max_mv ||
        recovery->max_temperature_dC >= config->over_temp_dC ||
        recovery->discharge_limit_ma <= 0 ||
        recovery->discharge_limit_ma >= config->discharge_limit_ma ||
        recovery->charge_limit_ma <= 0 ||
        recovery->charge_limit_ma >= config->charge_limit_ma ||
        recovery->voltage_max_age_ms == 0u ||
        recovery->temperature_max_age_ms == 0u ||
        recovery->current_max_age_ms == 0u ||
        recovery->stable_time_ms == 0u)
    {
        return 0u;
    }

    return 1u;
}

void Bms_ControllerInit(BmsController *controller)
{
    if (controller == NULL)
    {
        return;
    }

    Bms_StateMachineInit(&controller->machine);
    Bms_RecoveryInit(&controller->recovery);

    /* 首次检查尚未执行，不把未知数据报告为正常。 */
    controller->active_faults = BMS_FAULT_DATA_INVALID;
    controller->clear_allowed = 0u;
}

void Bms_ControllerStep(
    BmsController *controller,
    const BmsSample *sample,
    const BmsControllerConfig *config,
    BmsCommand command,
    uint8_t self_test_passed,
    uint32_t now_ms)
{
    BmsVoltageReport voltage;
    BmsTemperatureResult temperature;
    BmsCurrentResult current;
    BmsControlInput input = {0};

    if (controller == NULL)
    {
        return;
    }

    input.command = command;
    input.self_test_passed = self_test_passed;

    /* 缺少采样对象或配置错误，立即交给状态机锁定。 */
    if (sample == NULL || Bms_ControllerConfigIsValid(config) == 0u)
    {
        controller->active_faults = BMS_FAULT_INPUT_ERROR;
        controller->clear_allowed = 0u;
        Bms_RecoveryInit(&controller->recovery);

        input.active_faults = controller->active_faults;
        Bms_StateMachineStep(&controller->machine, &input);
        return;
    }

    /* 1：使用正常保护阈值，检查同一轮采样和同一个当前时间。 */
    voltage = Bms_CheckPackVoltages(
        sample, config->uv_threshold_mv, config->ov_threshold_mv,
        now_ms, config->voltage_max_age_ms);

    temperature = Bms_CheckTemperature(
        &sample->temperature_dC, config->over_temp_dC,
        now_ms, config->temperature_max_age_ms);

    current = Bms_CheckCurrent(
        &sample->current_ma,
        config->discharge_limit_ma, config->charge_limit_ma,
        now_ms, config->current_max_age_ms);

    controller->active_faults = Bms_CombineFaults(
        &voltage, temperature, current);

    /* 2：只有已经处于故障锁定时，才累计恢复时间。 */
    controller->clear_allowed = 0u;

    if (controller->machine.state == BMS_STATE_FAULT_LOCK)
    {
        controller->clear_allowed = Bms_RecoveryUpdate(
            &controller->recovery, sample, &config->recovery,
            controller->active_faults, now_ms);
    }
    else
    {
        Bms_RecoveryInit(&controller->recovery);
    }

    /* 3：统一交给状态机决定下一状态和软件输出许可。 */
    input.active_faults = controller->active_faults;
    input.clear_allowed = controller->clear_allowed;
    Bms_StateMachineStep(&controller->machine, &input);

    /* 清除成功后立即丢弃计时，避免下次故障复用旧记录。 */
    if (controller->machine.state != BMS_STATE_FAULT_LOCK)
    {
        Bms_RecoveryInit(&controller->recovery);
        controller->clear_allowed = 0u;
    }
}
```

辅助校验函数用 static 限制在本文件内。保护要求0<欠压阈值<过压阈值、两个电流限值为正、超时非零；恢复要求电压区间更窄、过温恢复值更低、两个电流恢复限值更小、超时及稳定时间非零。

初始化只调用一次。Step即使没有新指令也要周期执行；调用方传 NONE 表示没有新事件。自检阶段和过早 CLEAR 的指令不会被内部缓存，也不会在未来自动重放。

控制器计算完恢复许可后调用状态机；若清除成功，状态已经是 STANDBY，马上重置恢复记录，并把对外 clear_allowed 设为0。许可只属于当前锁定周期，不复用到下一次故障。

空采样对象或错误配置会产生 INPUT_ERROR；非空对象中的 valid=0 则由正常保护得到 DATA_INVALID。这是调用参数错误与测量质量错误的区别。

## SWD 接线与 Keil 识别

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

### 已从照片核对的信息

开发板正面有野火标志，两个Type-C接口分别标为左侧USB TO UART和右侧USB DEVICE。MCU完整丝印及PCB版本在当前照片中无法可靠辨认，后续补齐。

将开发板放成照片方向，两个USB接口朝上。它们之间的蓝色五针接口为J2，从左到右为：

```text
RST    TCK    GND    TMS    3V3
```

SWD模式下，TCK对应SWCLK（PA14），TMS对应SWDIO（PA13）。名称来自复用调试信号；当前工程保留PA13/PA14的Serial Wire接口。

用户的紫色Zave ST-LINK V2外壳标签给出以下功能表：

| 针脚编号 | 标签 |
| --- | --- |
| 1 | RST |
| 2 | SWCLK |
| 3 | SWIM |
| 4 | SWDIO |
| 5、6 | GND |
| 7、8 | 3.3V |
| 9、10 | 5.0V |

这是照片中的兼容调试器针脚表，不能直接替换成其他型号的排针顺序。插针端的观看方向与外壳图可能不同，接线按实物针脚编号定位；找不准编号时先补充插针端照片。

### 第一步：断电后接三根线

先拔掉开发板和ST-LINK的USB，使用三根母对母杜邦线连接：

| ST-LINK | 开发板J2 | 作用 |
| --- | --- | --- |
| 2号SWCLK | TCK | 调试器提供通信时钟 |
| 4号SWDIO | TMS | 双向传送调试命令和数据 |
| 6号GND，也可选5号 | GND | 提供共同的电压参考 |

SWD使用两根调试信号线，仍需要共地。即使两者稍后都接同一电脑，也把GND按表连接，形成明确的信号回路。

本轮RST留空，ST-LINK的3.3V/5V脚和板卡J2的3V3也留空。我们通过板卡USB供电，不把两个电源输出并接。这个方案针对照片中的调试器；带VTref输入的其他探针需按其手册连接参考电压。

保持现有BOOT跳帽，不接外部CH340、电位器、NTC或负载模块，不需要将核心板插入面包板。

### 为什么这一步不接3.3V

既定供电方案为：

- 开发板USB输入5V，经板载稳压器得到3.3V，为STM32供电。
- ST-LINK通过自己的USB供电。
- 两者之间连接SWCLK、SWDIO和GND，用于调试通信。

因此板卡已经有自己的3.3V电源，无需再由调试器提供电源。若调试器的3.3V脚是电源输出，再接到板卡3V3会把两个稳压输出直接并联。两路实际电压不可能完全一致，可能产生回灌；除非电路明确支持这种连接，否则不这样接。

必须区分两类接口：

| 接口功能 | 含义 | 板卡已通过USB供电时 |
| --- | --- | --- |
| 3.3V供电输出 | 从调试器向目标板送电 | 本方案不并接 |
| VTref / VAPP等目标电压参考输入 | 从目标板取得电压参考，用于调试器的目标接口 | 按具体调试器手册连接目标VDD |

不能仅凭“3.3V”标签断定兼容调试器内部电路，也不能把当前三线方案推广到所有探针。带目标电压参考输入的型号应按其手册连接，参见[ST官方UM1075第4.2节](https://www.st.com/resource/en/user_manual/um1075-stsw-link007.pdf)。本项目兼容调试器的内部原理图及电源输出能力尚未核实，当前也不计划用它给整板供电。

### 第二步：分别连接USB

1. 开发板通过左侧标有USB TO UART的Type-C口连接电脑，保持板卡电源开启。
2. ST-LINK通过自己的USB接同一电脑。
3. 检查D1是否亮起，并确认三根线没有错位或松脱。

左侧USB同时承担板卡供电及板载USB转串口功能；这一步使用它供电，不依赖COM口是否出现。右侧USB DEVICE本轮留空。

### 第三步：在Keil检查连接

打开项目的MDK-ARM/bms_bringup.uvprojx。此时先不点Download，也不进入调试会话：工程可能在进入调试时自动下载程序。

操作路径：

```text
Options for Target（Alt+F7）
  → Debug
  → Use: ST-Link Debugger
  → Settings
  → Debug
```

逐项检查：

| 设置或显示区域 | 本步操作 | 原因或意义 |
| --- | --- | --- |
| Use | ST-Link Debugger | 使用外接调试器连接实物 |
| Port | SW，部分版本显示SWD | 对应已接好的SWCLK与SWDIO |
| Max Clock，若有此项 | 先选不高于1 MHz的档位 | 为初次杜邦线连接选择较低通信速率；不是MCU运行时钟 |
| Connect | 若RST留空，选择Normal | under Reset需要通过目标NRST实现硬件复位 |
| Adapter / Serial Number / FW | 查看是否出现调试器信息 | 验证电脑到ST-LINK这一段 |

该设置入口与SW Device判据见[Arm/Keil官方教程第26节](https://www.keil.com/appnotes/files/apnt_230_v1.35.pdf)。教程使用另一款开发板，只参考Keil操作及识别判据，不套用其中的芯片ID、Flash算法或板卡接线。

### 截图配置核对结果

当前工程目标为STM32F103ZE，使用STM32F10x_512.FLM。截图中的高密度512k片内Flash算法与当前工程相符。

| 截图项目 | 显示值 | 含义与本步处理 |
| --- | --- | --- |
| Algorithm | STM32F10x High-dens…，512k，On-chip Flash | 用于对应F1高密度器件的片内Flash擦写，保留 |
| Flash Start | 0x08000000 | 本工程内部Flash起始地址，保留 |
| Flash Size | 0x00080000 | 524288字节，即512 KiB，保留 |
| Flash Address Range | 0x08000000～0x0807FFFF | 起始地址加容量减1，与工程一致 |

这只是当前工程与下载配置的核对，不是容量全片测试或芯片完整料号的实物确认。MCU清晰丝印和PCB版本仍待补充。

### 每个下载选项有什么作用

| 选项 | 当前设置 | 作用 |
| --- | --- | --- |
| Erase Sectors | 选中 | 擦除本次程序所需的Flash页/扇区，为写入做准备 |
| Program | 勾选 | 将固件内容写入Flash |
| Verify | 勾选 | 校验写入的内容是否与本次固件一致 |
| Reset and Run | 勾选 | 下载完成后请求目标复位并运行 |
| Erase Full Chip | 未选 | 本次不需要擦除整个Flash |
| Do not Erase | 未选 | 本次保留擦除步骤，不能假定旧Flash内容适合直接写入 |

RAM for Algorithm是给下载算法使用的临时工作区。Keil/ST-LINK会将擦写算法和缓冲数据放入目标RAM，再执行算法操作Flash。它不表示整个固件有32 KiB，也不把芯片的64 KiB SRAM改成32 KiB；下载后正常程序仍按自己的链接配置使用RAM。

下载配置和操作入口参见[Keil官方Flash下载教程](https://www.keil.com/support/man/docs/mcbtsx1001/mcbtsx1001_fp_download.htm)。该教程使用另一种芯片，仅参考通用选项意义与操作入口，不使用它的算法名称、RAM地址或容量。

## main 断点、单步与复位

本章按首次搭建时的工程讲解；其中 HSI、空主循环或未配置外设是当时的状态。当前已使用 HSE/PLL、周期 ADC 和 UART，见[开发记录](开发记录.md#current-status)。

本章的测试示例和验收方法统一收录于[测试记录](测试记录.md#t24)。

### 为什么下载后还要做这一步

编译把源代码转换为机器码，下载把固件写入芯片Flash，断点与单步则让我们观察CPU执行到哪里。写入完成与实际执行是不同的验收项。

STM32复位后先执行启动代码，完成运行环境初始化，再进入main()。断点让CPU执行到指定位置时暂停，Keil通过ST-LINK查看当前指令及寄存器等状态。它不会直接修改项目C代码。

本次使用现有代码，不新增LED或BMS调用，避免同时引入新的验证对象。

### 当前代码位置

打开项目中的Core/Src/main.c，不是电脑测试目录中带独立main()的测试文件。

本次只读核对的行号：

| 行号 | 可执行语句 | 作用 |
| --- | --- | --- |
| 74 | HAL_Init(); | 初始化HAL基础环境和系统时基等 |
| 81 | SystemClock_Config(); | 配置本工程时钟，当前使用内部HSI 8 MHz |
| 88 | MX_GPIO_Init(); | 执行当前GPIO初始化；现有代码仅开启GPIOA时钟 |
| 95附近 | while (1) | 当前为空循环，没有LED控制或BMS控制调用 |

后续修改可能改变行号，以语句内容为准。第一次断点放在HAL_Init();这一行，不放在注释、空行或大括号上；空循环也可能缺少对应的独立源码调试位置。

### 第一步：设置断点

在Keil编辑器打开main.c，将光标放到HAL_Init();行，按F9。应出现断点标记，通常为红色圆点；也可以双击该行左侧的断点边栏。

断点标记表示希望执行到这里暂停，是否命中还需进入实物调试确认。只在VS Code文本窗口点断点，不会自动成为本次Keil会话中的断点。

### 第二步：进入实物调试

保持开发板供电与SWD连接，在Keil按Ctrl+F5，或选择Debug → Start/Stop Debug Session。

本机现有设置选择ST-LINK目标驱动，Run to main与进入调试前更新Flash已启用，因此：

- 进入会话可能自动再次下载固件，这是已有配置的行为。
- 正常情况下会暂停在main()入口附近，通常可看到HAL_Init();附近的黄色执行箭头。
- 如果已经停在HAL_Init();，直接进行下一步，不要为了“命中”再按F5让它跑进空循环。

黄色箭头表示下一条待执行的源码语句。箭头停在HAL_Init();时，该次调用通常还没有执行完成。

如果会话已经在运行，先通过Debug → Stop暂停，再使用Debug → Reset CPU；若复位后仍未停到HAL_Init();，按F5运行到该断点。若出现连接、复位或下载错误，先保留原文，不修改电源接线或猜测故障根因。

RST若仍留空，Connect应与前一步三线方案匹配为Normal。实际修改情况尚未从用户截图确认。

### 第三步：单步执行初始化

CPU暂停在HAL_Init();时：

1. 按一次F10，正常应执行完HAL_Init()并停到SystemClock_Config();附近。
2. 再按一次F10，正常应执行完时钟配置，停到MX_GPIO_Init();附近。

F10是Step Over：会执行函数调用并等待返回，然后暂停在后续语句，不逐行展示函数内部。F11为进入函数内部，本步不需要使用。

源码行的对应位置可能受编译器调试映射影响，允许停在相邻的可执行位置；关键是初始化调用能够返回，执行位置按预期推进。不要仅凭文本光标移动判断单步成功，应观察调试执行箭头。

本步不要求在空while循环上设断点，也不需要执行到BMS控制器：目前main()没有调用它。

### 第四步：复位后再次到达

保留HAL_Init();的断点，在调试会话中选择Debug → Reset CPU。

- 如果复位后已经停在HAL_Init();附近，说明再次到达目标位置。
- 如果停在启动代码，按F5运行，应在HAL_Init();断点处暂停。
- 如果持续运行不暂停或出现错误，保留当前窗口和输出，反馈后再排查。

这一步验证复位后能够重新进入固件入口，当前仍在调试器参与的条件下，不等于已经验收断开调试器后的独立启动。

完成观察后，可以按Ctrl+F5退出调试会话回到编辑状态。

### 常用按键的区别

| 按键或菜单 | 本步用途 |
| --- | --- |
| F9 | 设置或移除当前行断点 |
| Ctrl+F5 | 进入或退出调试会话 |
| F10 | 执行当前语句，跨过函数内部 |
| F5 | 持续运行，直到断点或手动暂停 |
| Debug → Reset CPU | 让目标CPU重新开始复位流程 |
| Debug → Stop | 暂停正在运行的CPU |

快捷键与操作意义参见[Keil官方快捷键表](https://www.keil.com/support/man/docs/uv4/uv4_dg_shortkeys.asp)和[Keil调试菜单说明](https://www.keil.com/support/man/docs/uv4cl/uv4cl_ui_debug.htm)。

### 引脚与接线依据

使用本地《[野火]STM32F103ZET6核心板双USB款原理图》，共7页。LED区域在第6页，该页标题栏为V2.0、2023-11-04；不同页的版本标注不完全一致，实物PCB版本仍待补充。

第6页LED区域已渲染并目视核对：

| 板上器件 | MCU引脚 | 串联电阻 | 有效电平 |
| --- | --- | --- | --- |
| D3，BLUE | PB5 | R20，470 Ω | 低电平亮、高电平灭 |
| D4，BLUE | PB0 | R21，330 Ω | 低电平亮、高电平灭 |
| D5，BLUE | PB1 | R22，100 Ω | 低电平亮、高电平灭 |

本步只控制D3。它已焊在板上，无需新增LED、电阻、面包板或信号线；沿用开发板USB供电和已有SWD连接。

D3电流路径为3V3→LED→R20→PB5。PB5输出低电平时吸收电流，LED导通；输出高电平时两端压差不足，LED熄灭。由实际电路决定亮灭，不能假定所有LED都是高电平亮。

配套标准外设库例程的引脚与低有效定义可交叉参考，但其红绿蓝、SCL等旧注释不匹配当前三颗蓝灯。当前工程使用HAL，不复制旧例程的标准库初始化。

### 第一步：CubeMX配置PB5

打开现有MCU/projects/bms_bringup/bms_bringup.ioc，不另建项目。当前HSI 8 MHz及SYS Serial Wire配置保持。

在Pinout中选择PB5为GPIO_Output，再进入System Core → GPIO，设置PB5：

| 配置 | 选择 | 原因 |
| --- | --- | --- |
| GPIO output level | High | D3低有效，初始化时先保持熄灭 |
| GPIO mode | Output Push Pull | 引脚可主动输出高和低电平 |
| GPIO Pull-up/Pull-down | No pull-up and no pull-down | 推挽输出不依赖内部上拉下拉 |
| Maximum output speed | Low | 足够驱动慢速LED；不是闪烁频率 |
| User Label | LED_STATUS | 生成可读的端口和引脚名称 |

F1的Low档对应2 MHz输出速度等级，用来控制输出驱动特性，不会让D3自动以2 MHz闪烁。闪烁节奏由下面的程序延时决定。

在Project Manager → Code Generator确认Keep User Code when re-generating已勾选。目前.ioc中的KeepUserCode已经为true，界面再确认后生成。用户代码写在USER CODE标记范围内，CubeMX才按这些区域保留；参见[ST CubeMX手册](https://www.st.com.cn/resource/zh/user_manual/um1718-stm32cubemx-for-stm32-configuration-and-initialization-c-code-generation-stmicroelectronics.pdf)。

使用现有CubeF1 1.8.7生成代码，不在这一步同时升级库或修改时钟。

### 第二步：检查自动生成结果

main.h应出现类似定义，由CubeMX生成，不重复手写：

```c
#define LED_STATUS_Pin GPIO_PIN_5
#define LED_STATUS_GPIO_Port GPIOB
```

LED_STATUS_GPIO_Port表示GPIOB端口，LED_STATUS_Pin表示PB5引脚掩码。GPIO_PIN_5不是直接传数字5，而是第5位对应的位掩码，使用生成的名称即可。

用户本次启用了外设分文件生成：MX_GPIO_Init()实际位于Core/Src/gpio.c，声明在Core/Inc/gpio.h，main.c包含gpio.h并调用该函数。初始化在独立文件是正常生成形式，不需要移回main.c。新增gpio.c/h与已变化的.mxproject应随本次工程保存。

MX_GPIO_Init()应包含这些关键配置：

- 开启GPIOB外设时钟，保证GPIOB可以配置和使用。
- 将PB5的输出值预设为GPIO_PIN_SET，即高电平、D3灭。
- 将PB5配置为GPIO_MODE_OUTPUT_PP、GPIO_NOPULL、GPIO_SPEED_FREQ_LOW。
- 用HAL_GPIO_Init初始化GPIOB。

检查bms_types.h的用户区include和已有BMS C/H仍保留。回到Keil时允许重新载入工程；Application/User/Core应仍有先前添加的保护、状态机、恢复和控制器模块。若工程重新生成后没有保留用户添加的文件条目，按原方法把相应C/H重新加入，电脑测试文件不加入MCU工程。

### 第三步：编写带注释的循环

在VS Code打开Core/Src/main.c。保留HAL_Init()、SystemClock_Config()和MX_GPIO_Init()，将USER CODE BEGIN WHILE到USER CODE END 3这一段调整为：

```c
/* USER CODE BEGIN WHILE */
while (1)
{
  /* USER CODE END WHILE */

  /* USER CODE BEGIN 3 */

  /* D3低电平亮：把PB5拉低，让电流流过LED。 */
  HAL_GPIO_WritePin(LED_STATUS_GPIO_Port, LED_STATUS_Pin, GPIO_PIN_RESET);

  /* 保持亮灯约500毫秒；当前主循环在这里等待，SysTick中断继续计时。 */
  HAL_Delay(500u);

  /* D3高电平灭：把PB5拉高，LED两端不再有足够的导通电压。 */
  HAL_GPIO_WritePin(LED_STATUS_GPIO_Port, LED_STATUS_Pin, GPIO_PIN_SET);

  /* 保持灭灯约500毫秒，再进入下一轮。 */
  HAL_Delay(500u);
}
/* USER CODE END 3 */
```

这里GPIO_PIN_RESET表示输出低电平，不是复位CPU；GPIO_PIN_SET表示输出高电平。

HAL_GPIO_WritePin负责设定引脚状态，HAL_Delay等待以毫秒为单位的时基。现有SysTick_Handler会调用HAL_IncTick()，默认每1 ms更新HAL时基，HAL_Delay据此等待。

HAL_Delay是主循环忙等待，不是让CPU休眠或让出FreeRTOS任务；在等待期间，正常使能的中断仍可执行。本步用于验证GPIO和HAL时基，后续周期采样、控制任务会使用合适的非阻塞调度或RTOS延时。

两次500 ms合起来形成约1 s亮灭周期，不把HAL延时当作精密时间测量。D3当前仅是GPIO演示输出，尚未映射BMS状态，也不代表物理负载开关。

## USART1 固定文本发送

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

### 信号连接与硬件依据

依据双USB核心板原理图第5页J6、第7页CH340C，以及规格书V1.0.1第2.4.12～2.4.13节：

| MCU端 | 方向 | 板载CH340C端 | 跳帽 |
| --- | --- | --- | --- |
| PA9 / USART1_TX | MCU发送到电脑 | RXD | PA9↔RXD |
| PA10 / USART1_RX | 电脑发送到MCU | TXD | PA10↔TXD |

TX为发送端，RX为接收端，数据从一方TX到另一方RX。默认跳帽已经完成板载连接，先按实物丝印确认，不额外接杜邦线或外置CH340模块。

左侧USB TO UART口用于板卡供电和CH340C连接电脑；右侧USB DEVICE本步不使用。下载继续用ST-LINK的SWDIO、SWCLK、GND三线，RST留空，Normal连接。当前芯片自己的USB外设没有配置，电脑端口来自CH340C。

板上DTR/RTS连接ISP一键下载电路，可影响BOOT0和NRST。串口助手中关闭DTR/RTS控制、选择无流控；本步只读文本，不使用ISP下载按钮，BOOT跳帽保持现状。

### 第一步：配置USART1

退出Keil调试并保存文件，CubeMX打开现有bms_bringup.ioc。进入Connectivity → USART1：

| 配置 | 选择 | 原因 |
| --- | --- | --- |
| Mode | Asynchronous | UART异步通信，通过波特率约定时序，不需要额外时钟线 |
| Baud Rate | 115200 | 每秒传输位数，电脑端必须一致 |
| Word Length | 8 Bits | 每个数据单元8位 |
| Parity | None | 本步不加奇偶校验位 |
| Stop Bits | 1 | 每个数据单元以1个停止位结束 |
| Data Direction | Receive and Transmit / Tx and Rx | 初始化收发功能，本步代码只测试发送 |
| Hardware Flow Control | None / Disabled | 不使用CTS/RTS握手 |
| Over Sampling，若显示 | 16 Samples | 本F103配置保持16倍采样 |

8数据位、无校验、1停止位简称8N1。波特率描述位速率，一字节在8N1中还包含起始位与停止位，因此不等于每秒115200字节。

确认引脚为PA9/USART1_TX和PA10/USART1_RX，和板上跳帽一致；不重映射到其他引脚。保留PB5的LED_STATUS、HSI 8 MHz和Serial Wire。

本步不启用USART1全局中断，不配置DMA；HAL_UART_Transmit是轮询发送，等待硬件标志，不依赖USART1中断来完成发送。SysTick仍保留，为HAL超时与LED延时计时。

确认Keep User Code when re-generating后生成。当前项目按外设分文件生成，预计新增Core/Src/usart.c、Core/Inc/usart.h。

### 第二步：核对生成结果

main.c应自动包含usart.h，并在进入while之前调用MX_USART1_UART_Init()。现有HAL_Init、SystemClock_Config及MX_GPIO_Init保留。

usart.c/h中应有：

- UART_HandleTypeDef huart1及其extern声明：这是串口1的HAL句柄，保存所用外设与配置状态。
- Instance为USART1，参数为115200、8N1、Tx/Rx、无流控、16倍采样。
- 初始化USART1时钟及PA9复用推挽输出、PA10接收输入。
- HAL_UART_Init失败时调用Error_Handler。

stm32f1xx_hal_conf.h应由生成器启用HAL_UART_MODULE_ENABLED；Keil工程应加入usart.c和HAL UART驱动。以前的BMS和GPIO用户文件仍应保留，电脑测试文件不加入MCU工程。不要在生成前手工启用一部分HAL宏来绕过完整外设初始化。

### 第三步：编写固定消息发送

在main.c的PV用户区放入：

```c
/* USER CODE BEGIN PV */

/* 固定发送内容：\r\n让电脑收到后换到下一行。 */
static const uint8_t uart_message[] = "BMS UART1 OK\r\n";

/* USER CODE END PV */
```

static限制该变量的文件可见范围，const表示程序不修改消息内容，uint8_t数组存放字节。当前本地HAL_UART_Transmit的pData参数为const uint8_t*，可以直接传数组，不需要强制转换。

把WHILE用户区改为：

```c
/* USER CODE BEGIN WHILE */
while (1)
{
  /* USER CODE END WHILE */

  /* USER CODE BEGIN 3 */

  /*
   * 通过串口1发送一行消息。
   * sizeof减1：不发送字符串末尾的\0。
   * 100u：最多等待约100毫秒，单位不是字节数。
   */
  if (HAL_UART_Transmit(&huart1,
                        uart_message,
                        (uint16_t)(sizeof(uart_message) - 1u),
                        100u) != HAL_OK)
  {
    /* 本次基础实验发送失败时停在错误处理，便于用调试器定位。 */

  /* D3低电平亮，保持约500毫秒。 */

  HAL_Delay(500u);

  /* D3高电平灭，保持约500毫秒。 */
```

| 参数 | 含义 |
| --- | --- |
| &huart1 | 使用串口1的句柄 |
| uart_message | 发送数据的起始位置 |
| sizeof(uart_message)-1u | 发送14字节，排除末尾NUL；这是当前作用域中的真实数组大小 |

## 毫秒计时与独立周期

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

本章的测试示例和验收方法统一收录于[测试记录](测试记录.md#t28)。

### 本步目标与边界

只修改main.c的用户区，取消两次HAL_Delay(500u)，让D3每500 ms翻转、USART1每200 ms发送一次。两个动作各用一份时间记录；只改变串口周期不会同时改变LED周期。本步不修改CubeMX、接线、时钟、串口参数或中断。

这为后续主循环加入采样和保护留出执行机会。HAL_UART_Transmit仍为轮询发送，整个主循环没有变成完全不阻塞的系统；这也不是FreeRTOS任务调度。

### 原理与本地依据

本机CubeF1 1.8.7：

- Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal.c：HAL_InitTick默认配置1 ms SysTick；HAL_IncTick增加uwTick；HAL_GetTick直接返回uwTick；HAL_Delay在while中反复读时间直到满足延时。
- Core/Src/stm32f1xx_it.c：SysTick_Handler调用HAL_IncTick。
- Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal_uart.c：HAL_UART_Transmit等待TXE及TC标志，为阻塞发送。
- Core/Src/gpio.c：LED初始化为高电平，即D3熄灭；之后每次Toggle在亮与灭间切换。

HAL_Delay(500u)期间中断仍可运行，但主循环停在延时函数里。换成if判断后，到时间才执行动作，没到时间就继续向下运行，再进入下一轮。

每个周期的判断都是“当前计数减上次计数是否达到周期”。例如上次100 ms、现在600 ms，差值500 ms，需要翻转一次。

### 修改位置与完整代码

退出Keil调试，在VS Code打开Core/Src/main.c。保留HAL_Init、SystemClock_Config、MX_GPIO_Init、MX_USART1_UART_Init及原有include。所有新增内容放在对应USER CODE区内，避免再次生成时丢失。

PD区放周期常量：

```c
/* USER CODE BEGIN PD */

/* 单位都是毫秒；LED每翻转两次才完成一次亮灭。 */
#define LED_PERIOD_MS   500u
#define UART_PERIOD_MS  200u

/* USER CODE END PD */
```

PV区保留消息并增加两个时间记录，替换此区即可，不要重复定义uart_message：

```c
/* USER CODE BEGIN PV */

/* 保留原来的固定消息，末尾的回车换行用于电脑显示。 */
static const uint8_t uart_message[] = "BMS UART1 OK\r\n";

/* 分别记住上一次翻转LED、发送串口消息的时间。 */
static uint32_t led_last_ms = 0u;
static uint32_t uart_last_ms = 0u;

/* USER CODE END PV */
```

在两个外设初始化调用之后的USER CODE BEGIN 2区建立计时起点：

```c
/* USER CODE BEGIN 2 */

/* 外设初始化完成后，从此刻开始计算两个周期。 */
led_last_ms = HAL_GetTick();
uart_last_ms = led_last_ms;

/* USER CODE END 2 */
```

把原来的while用户区整体替换如下，移除旧的无条件发送和两次HAL_Delay：

```c
/* USER CODE BEGIN WHILE */
while (1)
{
  /* USER CODE END WHILE */

  /* USER CODE BEGIN 3 */

  /* 读取当前毫秒计数；读取时间不会等待。 */
  uint32_t now_ms = HAL_GetTick();

  /* 距离上次翻转已经过了500毫秒，才改变一次灯的状态。 */
  if ((uint32_t)(now_ms - led_last_ms) >= LED_PERIOD_MS)
  {
    /* 记下本次时间；未到下一周期时，主循环可以做其他事。 */
    led_last_ms = now_ms;
    HAL_GPIO_TogglePin(LED_STATUS_GPIO_Port, LED_STATUS_Pin);
  }

  /* 串口使用自己的计时，不必等LED完成一轮亮灭。 */
  if ((uint32_t)(now_ms - uart_last_ms) >= UART_PERIOD_MS)
  {
    uart_last_ms = now_ms;

    /* 发送仍然采用轮询方式；100u是超时上限，不是固定等待时间。 */
    if (HAL_UART_Transmit(&huart1,
                          uart_message,
                          (uint16_t)(sizeof(uart_message) - 1u),
                          100u) != HAL_OK)
    {
      /* 本次基础实验发送失败时停在错误处理，方便调试定位。 */
      Error_Handler();
    }
  }
}
/* USER CODE END 3 */
```

main.c使用的头文件已经提供uint32_t与HAL函数声明，不需要额外添加头文件。当前Keil工程已启用C99，允许在循环块中声明now_ms。

### 逐项理解

| 写法 | 含义 |
| --- | --- |
| LED_PERIOD_MS | 每次翻转间隔500 ms，完整亮灭周期约1000 ms |
| UART_PERIOD_MS | 发送间隔200 ms，约每秒5条，本步用于直观看到独立周期 |
| led_last_ms / uart_last_ms | 两个动作各自的上一次执行时间，不能共用一个last变量 |
| now_ms | 本轮统一读取的时间快照 |
| >= | 即便循环没有恰好碰上周期边界，超过周期也能执行 |
| 两个独立if | 同一轮两个动作都到时间时，都可以执行；不能改成else if而使其中一个依赖另一个 |
| HAL_GPIO_TogglePin | 翻转GPIO输出；D3低有效，每翻转一次改变亮灭状态 |
| last_ms = now_ms | 从本次检查时间重新计时，错过多个周期也只执行一次，不集中补发 |

这里使用从本次实际检查时刻重新计时的简单策略，存在主循环耗时引起的小幅延后和累计漂移，不称为精确周期调度。首次串口消息在初始化后约200 ms，首次D3翻转约500 ms；此前固定消息在进入循环时立即发送，启动时序不同是预期行为。

#### 为什么使用无符号相减

HAL_GetTick为uint32_t毫秒计数，约49.7天回绕。以当前0x00000020、上次0xFFFFFFF0为例，无符号差值为0x30，即48 ms，仍能算出跨回绕的间隔。短周期且持续检查时可使用这种写法；不能在不检查的情况下跨过完整计数周期后还指望恢复真实经过时间。

避免直接写now_ms >= last_ms + period_ms，因为截止时间加法回绕后可能误判。强制转换用于明确按uint32_t差值处理。

#### 串口发送仍会占用主循环

消息14字节，115200/8N1每字节需要起始位、8数据位、停止位，共10位。理论线传输时间为14×10/115200秒，约1.22 ms，实际还受代码和时钟影响。100u为超时上限，不表示每次发送固定等100 ms。异常返回时仍进入现有Error_Handler，作为本次调试策略。

主循环现在可以在两次到期之间执行其他工作，但不能据此宣称采样保护时限已经满足。CPU仍反复执行while，没有休眠；后续接入真实控制时再核对每项耗时，并按需要采用中断/DMA或FreeRTOS。

### 接线与下载

沿用左侧USB TO UART、板载CH340C、PA9/PA10跳帽和现有COM口，电脑仍为115200/8N1、文本显示、无流控、DTR/RTS关闭控制。SWD仍为三线，RST留空。

用户F7构建、F8下载；如果在调试会话中暂停，F5继续运行后再观察。不要在断点暂停期间评价输出周期。

## HSE 与 72 MHz 系统时钟

按首次实现顺序保留操作、原理与代码示例。当前完成程度见[开发记录](开发记录.md#current-status)，当前接口以仓库源码为准。

### Clock Configuration逐项设置

切到Clock Configuration，从输入到输出检查。页面不同版本的文字位置可能不同，目标数值与来源选择保持如下：

| 配置 | 选择 | 结果与原因 |
| --- | --- | --- |
| HSE Input frequency | 8 MHz | 与板载晶体标注一致 |
| PLL Source Mux | HSE | PLL使用外部高速晶体作为参考 |
| HSE到PLL的分频 | /1 | 进入PLL仍为8 MHz，避免误选/2 |
| PLL倍频 | ×9 | 8×9=72 MHz |
| System Clock Mux | PLLCLK | 系统实际改用PLL输出；只启用PLL而不选择它仍不能切换 |
| AHB Prescaler | /1 | HCLK=72 MHz，作为内核及AHB域时钟 |
| APB1 Prescaler | /2 | PCLK1=36 MHz，满足该总线限制 |
| APB2 Prescaler | /1 | PCLK2=72 MHz，USART1在该域 |
| ADC Prescaler，页面可配置时 | /6 | ADC时钟12 MHz，低于14 MHz上限；本步不启用ADC采样 |

核心关系：

```text
Y1 8 MHz → HSE /1 → PLL ×9 → SYSCLK 72 MHz
                              └ AHB /1 → HCLK 72 MHz
                                           ├ APB1 /2 → PCLK1 36 MHz
                                           └ APB2 /1 → PCLK2 72 MHz
```

不要只填右侧72 MHz而不检查HSE来源和分频。若自动求解，求解后仍按表逐项核对。若当前未启用ADC导致其节点不可编辑，本步先不加ADC外设；下次启用ADC时设置/6，核对实际生成的ADC时钟代码。ADC节点目标并不等于本步已经执行ADC初始化或采样。

APB1分频不为1时，相关定时器时钟可能为PCLK1的两倍，即72 MHz；PCLK1与定时器计数时钟不能混为一谈，后续TIM实验再核对。左侧USB转串口依然由板载CH340C承担，本步不启用MCU USB设备外设。

### 为什么LED与串口不应该变快9倍

本机CubeF1 1.8.7的HAL_RCC_ClockConfig在切换后，按硬件寄存器计算并更新SystemCoreClock，随后调用HAL_InitTick重新配置毫秒时基。因此HAL_GetTick仍以毫秒为单位，LED和消息周期常量不变。

USART1初始化位于时钟配置之后。HAL_UART_Init使用新的PCLK2计算波特率分频，因此目标仍为115200；电脑串口助手无需改为原来的9倍。

这是本次要复测的行为，不凭代码生成成功宣布时基与波特率已通过。HAL_UART_Transmit仍为阻塞方式，增加CPU频率也不使串口字节以更高的目标波特率发送。

### 用户编写代码

#### 增加调试观察变量

在main.c现有USER CODE BEGIN PV区追加以下内容，保留uart_message和两个计时变量：

```c
/* 初值超出12位ADC范围，方便确认采样代码确实执行过。 */

```

uint32_t与HAL_ADC_GetValue的返回类型一致。volatile让程序保留对该变量的实际访问，便于调试观察；它不提供任务互斥或线程安全。0xFFFFFFFF为本步调试用“尚未采样”标记，不是有效测量值。后续采用正式BmsMeasurement有效标记与时间戳。

#### 初始化中完成一次采样

把main.c的USER CODE BEGIN 2区域替换为下列内容，确保所有MX初始化调用在它之前：

```c
/* USER CODE BEGIN 2 */

    /* 上电后做一次ADC内部校准，减小内部偏差。 */
    if (HAL_ADCEx_Calibration_Start(&hadc1) != HAL_OK)
    {
        Error_Handler();
    }

    /* 软件启动一次转换。 */
    if (HAL_ADC_Start(&hadc1) != HAL_OK)
    {
        Error_Handler();
    }

    /* 等待本次转换完成；10u是超时上限，单位为毫秒。 */
    if (HAL_ADC_PollForConversion(&hadc1, 10u) != HAL_OK)
    {
        Error_Handler();
    }

    /* 读取原始数字量。12位、右对齐时，正常范围为0～4095。 */
    adc_raw = HAL_ADC_GetValue(&hadc1);

    /* 本次读取结束，关闭ADC，后续需要采样时再启动。 */
    if (HAL_ADC_Stop(&hadc1) != HAL_OK)
    {
        Error_Handler();
    }

    /* 保留原有LED和串口计时，从初始化完成后开始计时。 */
    led_last_ms = HAL_GetTick();
    uart_last_ms = led_last_ms;

/* USER CODE END 2 */
```

这些代码只在每次启动/复位时执行一次。改变接线后需要复位或重新上电，adc_raw才会更新；F5继续while并不会再采一次。

校准、启动、等待、读取、停止各自负责不同阶段。PollForConversion采用阻塞等待，10 ms为超时上限，正常转换约几十微秒量级；本步在启动阶段验证，不将其宣称为实时采样或最终保护策略。Error_Handler沿用当前外设验证方式，后续采样失败改为报告无效或超时故障。

保留原来的while：LED500 ms翻转、UART200 ms发送固定文本。串口此时仍不输出adc_raw。

裸电位器完全脱离其他电路、保持断电。万用表黑表笔接COM，红表笔接带V/Ω标识的测量孔，选择20 kΩ电阻量程或自动电阻挡；如Ω与蜂鸣/二极管共用位置，用仪表对应功能键切换至Ω。不要使用A/10A专用插孔或电流挡；电阻测量期间不给电位器或其相连电路供电。

随后识别：

1. 找到旋转时阻值基本保持约10 kΩ的一对端子，记为固定端A、B。
2. 找到分别与A、B之间阻值随旋转变化的端子，记为滑动端W。A-W增大时，B-W通常相应减小。
3. 若有额外端子，可能属于开关或机械结构，先按具体器件核对，不把它们随意接电源。
4. 记录A-B总阻值，以及W-A和W-B随旋转的变化；在器件或记录图中标清A/B/W后再接电。万用表暂不使用，实测值与实际物理位置尚未提供，识别暂缓。

确认A/B/W后，断开板卡及ST-LINK的USB供电，移除此前PC0到GND或3V3的直连，再接：

| 功能端 | 连接 |
| --- | --- |
| 固定端A | 开发板3V3 |
| 固定端B | 开发板GND |
| 滑动端W | PC0 |

A、B交换只改变旋转方向对应的电压变化方向。PC0的旧直连必须移除，避免滑动端被固定电平钳住。所有信号限定在同板3.3 V参考范围，电位器不使用5V供电。

测阻结束先移开表笔。通电后需要核对W对GND电压时，改用直流电压挡，黑表笔接GND、红表笔接W；电阻识别和带电电压测量分开进行。

面包板上三个电气节点分别落在不相通的连接组。若器件脚距不适配，应先做可靠的转接连接，不强行插入。实际脚位与接线验证完成前，电位器验收保持待完成。

### 修改采样窗口

CubeMX打开现有.ioc，ADC1的规则转换Rank 1仍为Channel 10，将Sampling Time从当前1.5改为239.5 Cycles。其余保持：

- PC0/ADC1_IN10、单通道、软件触发、右对齐、关闭连续/扫描/间断转换。
- ADC时钟PCLK2/6=12 MHz。
- HSE/PLL与USART1保持现有参数，不启用ADC中断或DMA。
- 用户代码保留，保存生成。

生成后adc.c应为ADC_SAMPLETIME_239CYCLES_5。较高源阻抗需要足够时间给内部采样电容充电。10 kΩ电位器作为分压器时，中间位置的等效源阻抗约2.5 kΩ（忽略其他负载）；长采样窗口有利于本次慢变化输入实验。

100 ms是软件两次启动之间的间隔，239.5周期是每次内部采样窗口，不能混为一谈。12 MHz下，加上12.5个转换周期，单次理论约21 µs，程序还有其他开销。

### 代码理解与实际限制

- LED、ADC、UART各自保存上次执行时间。ADC更新数据，UART发送最近一次成功读到的数据；同轮ADC在UART前执行。
- ADC首次正常读取前，adc_raw为0xFFFFFFFF，发送条件阻止打印尚未初始化的测量。
- ADC转换仍采用轮询等待；UART仍阻塞发送。当前没有完整实时性保证或FreeRTOS任务，初始化/读取失败仍进入Error_Handler，作为外设验证策略。后续把失败改为无效、超时及故障处理。
- adc_mv按raw×3300/4095作满量程线性显示估算，加半个分母作四舍五入。最大乘积加舍入项约1352万，适合uint32_t；尚未做基准、电阻与ADC误差标定。
- 3300是参考电压假定值，不是已实测的VREF+。当前输入引脚电压与电池单体电压是不同测量对象，后续再实现量程映射或真实分压采样。
- snprintf缓冲区为64字节，返回值为本应生成的文本长度（不含末尾NUL）；负数表示失败，达到或超过容量表示截断。发送前检查，并只发送实际长度。
- %lu与unsigned long参数配对；const uint8_t*转换是将字符缓冲区交给按字节发送的HAL接口，数据内容不变。
- 使用整数毫伏显示，不引入浮点格式化。volatile只便于观察，不提供并发互斥。
- 到期执行一次，不集中补发延误周期，主循环耗时可能引入延后；USB/串口助手显示也有缓冲，不把目测行间隔作为精确计时。

例如raw为0、2048、4095时，按本步公式显示约0、1650、3300 mV。这是换算示例，不是已经测得的三点数据。

```c
                DEMO_SELF_TEST_PASSED,
                now_ms);
        }
```

command先保存本轮命令，随后将调试入口清零，再传入控制器。这样调试入口虽恢复NONE，本轮仍能处理刚取出的START/STOP，下一轮不会重复处理旧命令。不要把调试命令写入state或load_enabled，状态和输出许可仍由状态机决定。

### 3. 编译、下载与调试验证

1. F7完整构建，0错误0警告后下载，进入Keil调试，F5运行，先等串口显示正常待机。
2. 通过View → Watch Windows → Watch 1加入bms_debug_command、bms_controller.machine.state、bms_controller.machine.load_enabled。
3. 暂停目标，在command = bms_debug_command;这一行F9设置断点，再F5运行到该行，停在取命令之前。
4. 在Watch的bms_debug_command的Value栏输入1并按回车，即START；在该行F9取消断点，F5连续运行，观察state=2、faults=0、load=1。
5. 再按同样方式停在取命令行，把入口改成2，即STOP；取消断点并F5，观察state=1、faults=0、load=0。
6. 命令处理后入口恢复NONE/0是预期结果，运行状态应持续保持直到另一条命令或故障。调试暂停期间串口与心跳停止更新是正常现象，恢复连续运行后再验收。

| 写入值 | 命令 | 正常数据下的预期 |
| --- | --- | --- |
| 0 | NONE | 不发新指令，保持当前状态 |
| 1 | START | 从待机进入运行，软件许可为1 |
| 2 | STOP | 从运行回待机，软件许可为0 |

先进入待机再发START，因为自检阶段同一轮只允许转入待机，不会继续启动。使用断点在取命令之前改值，可避免暂停位置恰好位于读取和清空之间而丢失输入。以后接中断或任务时，应单独设计正式命令传递。

程序没有把load_enabled写入实际GPIO；load=1只表示软件许可，D3继续500 ms心跳。模拟自检输入仍是演示常量，真实自检和负载控制未实现。预期输出与记录位置见[测试记录](测试记录.md#debug-start-stop)。

#### 按顺序执行故障阶段

1. 正常启动：电压保持3800，写命令1，取消断点并F5。确认state=2、faults=0、latched=0、load=1、clear=0。

8. 再次启动：写命令1，F5运行。预期state=2、load=1，其余故障字段为0。

当前过压触发条件为>=4200 mV，恢复上界为严格小于4100 mV；4150不触发当前过压，却始终不满足恢复上界。3800满足恢复范围，且其他模拟通道正常、新鲜，持续运行足够时间后才允许清除。CLEAR只返回待机，不自动运行；退出锁定后clear回0是正常行为。load仍只是软件许可，D3仍是心跳，没有验证实际负载断开。

| 正常3800 mV，发START=1 | 2 | 0 | 0 | 1 | 0 |
| 第一节改4300 mV | 3 | 1 | 1 | 0 | 0 |
| 保持4300 mV，发CLEAR=3 | 3 | 1 | 1 | 0 | 0 |
| 改4150 mV，连续运行至少3 s | 3 | 0 | 1 | 0 | 0 |

### 6. 各阶段状态与变量变化

串口state、faults、latched、load、clear分别对应machine.state、active_faults、machine.latched_faults、machine.load_enabled、clear_allowed。状态值0/1/2/3分别是自检、待机、运行、故障锁定。命令值0/1/2/3分别是NONE、START、STOP、CLEAR；命令3和状态3属于不同变量。

每轮控制顺序为：生成模拟快照→取出并清空调试命令→按正常阈值计算活动故障→锁定期间检查恢复条件→状态机处理故障和命令→退出锁定时重置恢复记录。控制周期配置100 ms，UART周期配置200 ms，不代表已精确测得响应时间。

- 启动：初始化先到SELF_TEST，历史故障为0，负载许可为0；active_faults暂设DATA_INVALID表示尚未检查。第一轮正常快照重新计算活动故障为0，演示自检标志1使状态转到STANDBY。该标志不是硬件自检结果。
- START：3800 mV时无故障，在待机消费命令1后进入RUN，load=1。下一轮没有新命令仍保持运行。
- 4300 mV：达到过压阈值4200，active_faults=0x1；故障优先于命令，状态进入FAULT_LOCK，latched_faults按位或累计为0x1，load=0。此时CLEAR不能解除锁定，恢复计时保持复位。
- 4150 mV：低于4200，正常检查使active_faults回0；latched_faults不随之清除，状态继续锁定。恢复要求电压严格小于4100，因而计时不启动，等再久clear仍0；此时CLEAR也无效。
- 3800 mV刚恢复：恢复检查全部通过时，recovery.timing从0变1，stable_since_ms记录本轮now_ms；clear仍0。后续稳定期间起点不变，当前时间继续增长，差值达到配置2000 ms后clear变1。state仍为FAULT_LOCK，历史故障仍0x1，load仍0；如果中途任一恢复条件失败，计时丢弃、从头开始。
- 合格后CLEAR：同时满足无活动故障、自检通过、恢复许可1和命令CLEAR，状态回STANDBY，latched_faults清0，load仍0。控制器发现已经离开锁定，立即将timing、stable_since_ms、clear_allowed都清0，避免下一次故障复用旧许可。
- 再次START：待机且无活动故障时进入RUN，load变1；CLEAR本身不自动重启。

调试入口bms_debug_command是一次性命令：例如Watch写3，main先复制到局部command，再将入口清0，因此局部副本仍能把CLEAR传给控制器。入口归零只表示本轮已取走命令，不代表一定执行成功；被拒绝的CLEAR不会排队等恢复，恢复后需要重新发送。

bms_sim_cell0_mv是第一节的可调输入，bms_sample.cell_mv[0].value是本轮生成的快照，前者修改后到下一次生成快照才传入保护逻辑。其他两节仍3800 mV，电流0 mA，温度250即25.0℃；各测量valid=1、source=SIMULATED，timestamp_ms随每轮新快照刷新。本实验没有用ADC生成这些快照，也没有注入采样超时。

测量timestamp_ms表示这次采样何时生成，每轮更新；recovery.stable_since_ms表示这段连续健康条件从何时开始，在本段计时内固定。两者用途不同。timing=1表示已经开始计时，是否满2000 ms由时间差决定；clear=1才表示本轮具备恢复许可。

## USART1接收中断：用单字符命令控制BMS

日期：2026-10-20。当前代码基线为d050d1a，上一轮解释文档已由用户保存于1c1f9f4。本章是下一步教程：助手未修改源码、.ioc或工程配置，用户实现和板上验收均待完成。

目标：电脑串口助手发送大写S启动、T停止、C清除故障，交给现有控制器判断是否执行。继续使用板载USB TO UART和现有接线、115200/8N1；不新增外接模块。本步每次只发送一个字符，观察新状态后再发下一条，单槽入口只保留最新一条待处理命令，连续命令队列留待后续。

### 1. CubeMX打开USART1全局中断

打开现有MCU/projects/bms_bringup/bms_bringup.ioc，进入Connectivity → USART1 → NVIC Settings，勾选USART1 global interrupt，抢占优先级设5、子优先级0。当前NVIC_PRIORITYGROUP_4下有效抢占优先级为0～15，数字越小越优先，子优先级使用0。本步不修改现有时钟、ADC、引脚和波特率。

确认Project Manager → Code Generator的Keep User Code when re-generating已勾选，再生成代码。生成后核对Core/Src/usart.c包含HAL_NVIC_SetPriority(USART1_IRQn, 5, 0)和HAL_NVIC_EnableIRQ(USART1_IRQn)；Core/Src/stm32f1xx_it.c包含下列调用。它由CubeMX生成，只核对，不再手动添加第二个同名函数。

```c
void USART1_IRQHandler(void)
{
    HAL_UART_IRQHandler(&huart1);
}
```

中断控制器允许USART1中断后，仍需HAL_UART_Receive_IT启动一次接收。数据到达时，USART1_IRQHandler把中断交给HAL，HAL收满设定长度后再调用应用回调。

### 2. main.c增加接收缓冲与恢复请求

在USER CODE BEGIN PV区域、现有bms_debug_command声明旁增加：

```c
/* HAL把收到的一个字节写到这里；接收结束后由回调读取。 */
static uint8_t uart_rx_byte = 0u;

/* 中断只提出重启接收的请求，具体恢复放在主循环完成。 */
static volatile uint8_t uart_rx_restart_required = 0u;
```

原bms_debug_command变量继续使用，将其注释改为“单槽命令入口：由Watch或串口中断写入，主循环取走后清空”。uart_rx_byte为static，保证异步接收期间内存一直存在；恢复请求由中断写、主循环读写，因此使用volatile。

### 3. 保护命令的取出与清空

在USER CODE BEGIN 0中、Bms_MakeSimulatedSample定义之前增加：

```c
/* 取走待处理命令；避免取出和清空之间被串口中断插入。 */
static BmsCommand Bms_TakePendingCommand(void)
{
    BmsCommand command;
    uint32_t saved_primask = __get_PRIMASK();

    /* 这里只保护几个内存操作，随后马上恢复原来的中断状态。 */
    __disable_irq();
    command = bms_debug_command;
    bms_debug_command = BMS_CMD_NONE;
    __set_PRIMASK(saved_primask);

    return command;
}
```

volatile要求真实读写变量，但不能把“取出、清空”两个操作合并成一个不可打断的动作。现在UART中断也会写命令，如果刚复制旧值就插入新命令，再清空会丢掉新命令。短暂关闭中断能保护这两个操作；保存并恢复PRIMASK能保留调用前的中断状态。

在100 ms控制分支中，将原command=bms_debug_command及紧接的入口清零语句，替换为：

```c
            /* 取出并清空命令，避免与串口中断发生竞争。 */
            command = Bms_TakePendingCommand();
```

保留原局部BmsCommand command声明、模拟采样生成及Bms_ControllerStep传参。

### 4. 启动第一次接收

在USER CODE BEGIN 2中、Bms_ControllerInit及三个周期时间初始化之后增加：

```c
    /* 第一次启动单字节接收；函数立即返回，不等待电脑发送。 */
    if (HAL_UART_Receive_IT(&huart1, &uart_rx_byte, 1u) != HAL_OK)
    {
        Error_Handler();
    }
```

_IT表示使用中断，1u表示收满一个字节就完成；调用后立即返回，主循环可以继续工作。

### 5. 增加接收和错误回调

在main.c底部USER CODE BEGIN 4区域增加下面两个全局函数，不加static，不修改HAL驱动里的弱定义：

```c
/* 收满一个字节时，HAL会在USART1中断中调用这个函数。 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance != USART1)
    {
        return;
    }

    /* 本次伴随UART错误时，丢弃该字节，交给主循环恢复接收。 */
    if ((huart->ErrorCode != HAL_UART_ERROR_NONE)
        || (uart_rx_restart_required != 0u))
    {
        uart_rx_restart_required = 1u;
        return;
    }

    /* 中断只转换命令，不在这里执行状态机或打印日志。 */
    switch (uart_rx_byte)
    {
        case 'S':
            bms_debug_command = BMS_CMD_START;
            break;

        case 'T':
            bms_debug_command = BMS_CMD_STOP;
            break;

        case 'C':
            bms_debug_command = BMS_CMD_CLEAR;
            break;

        default:
            /* 换行和其他字符直接忽略，不覆盖已有命令。 */
            break;
    }

    /* 上一次只接收一个字节，完成后需要再次启动下一次接收。 */
    if (HAL_UART_Receive_IT(&huart1, &uart_rx_byte, 1u) != HAL_OK)
    {
        uart_rx_restart_required = 1u;
    }
}

/* UART检测到溢出、帧错误等情况时，提出恢复请求。 */
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART1)
    {
        uart_rx_restart_required = 1u;
    }
}
```

回调中的switch把字符转换为既有BmsCommand枚举，随后立即续接下一字节。中断里不执行控制器，也不进行阻塞串口发送。C只是清除请求，故障优先和恢复门控仍由原状态机执行。

### 6. 主循环处理接收恢复请求

在while循环内、uint32_t now_ms=HAL_GetTick()之后、原LED周期判断之前增加：

```c
        /* UART异常或接收续接失败时重启接收；失败则下一轮再试。 */
        if (uart_rx_restart_required != 0u)
        {
            /* 先清请求；之后若又产生新请求，仍能保留下来。 */
            uart_rx_restart_required = 0u;

            if ((HAL_UART_AbortReceive(&huart1) != HAL_OK)
                || (HAL_UART_Receive_IT(
                        &huart1, &uart_rx_byte, 1u) != HAL_OK))
            {
                uart_rx_restart_required = 1u;
            }
        }
```

错误回调只设置请求；主循环终止当前接收后重新挂接同一个缓冲区。代码检查重启返回值，失败则保留请求下轮重试。本步不宣称已经完成串口错误注入、帧协议、命令排队或完整通信故障策略。
